# 嵌入式软件架构与设计模式规范

> 版本：v1.3.0<br>
> 创建日期：2026-07-18<br>
> 最后更新：2026-07-19<br>
> 状态：Active<br>
> 适用范围：个人 STM32、TI MSPM0、ESP32 及其他 MCU 的裸机/RTOS C 项目

本文档规定嵌入式软件如何分层、组织模块、隔离硬件、处理并发和演进。代码的命名、排版、注释和类型规则见
[CODING_STYLE.md](CODING_STYLE.md)。本文档提供可映射到不同芯片、厂商 SDK 和 RTOS 的个人架构基线；具体平台 API 的使用方法由对应官方文档说明。

## 1. 使用方式与规则等级

### 1.1 规则等级

- **MUST**：默认必须遵守。
- **SHOULD**：通常应遵守；需要有明确理由才能偏离。
- **MAY**：可选实践，按项目规模决定。
- **EXCEPTION**：记录平台、性能或交付原因后允许的例外。

严格约束的是依赖方向、数据所有权、并发边界、错误传播和硬件隔离；文件数量、抽象层数量和测试深度可以随项目规模裁剪。例外记录至少包括原因、影响、替代方案、验证方式和计划失效日期。

### 1.2 版本和维护

本文档采用 SemVer：`MAJOR` 表示架构原则或章节体系不兼容变化，`MINOR` 表示新增模式或扩展，`PATCH` 表示文字、示例和链接修正。新增主题放入稳定章节，不因增加 RTOS、测试或新平台而重写目录；废弃内容先标记 `Deprecated`，并在变更记录中保留迁移说明。

## 2. 目标与架构原则

嵌入式架构必须同时满足以下目标：

1. 业务逻辑不依赖具体芯片、引脚或厂商 HAL。
2. 硬件替换只影响 BSP、驱动或适配器，不迫使应用层重写。
3. 中断、DMA、主循环和 RTOS 任务之间的责任清晰可审查。
4. 时间、内存、栈、队列和带宽等资源有可解释的上限。
5. 异常、超时和硬件故障有明确的传播和恢复路径。
6. 领域逻辑能够在主机环境中尽可能独立测试。
7. 架构能够从裸机逐步迁移到 RTOS，并将 RTOS API 限制在调度、同步和平台适配边界。

核心判断标准是：**上层依赖能力，不依赖实现；模块通过窄 API 协作，不通过共享内部数据协作。**

## 3. 工程规模分级

### 3.1 最小配置

适用于竞赛、实验和约 1～7 天的项目：

- 可以合并 `app`、`modules` 或 `services` 中的少量文件。
- 至少保留平台初始化、设备驱动、业务逻辑和配置的边界。
- 至少定义关键模块 API、主要状态机、通信格式和最终冒烟测试。
- 可以不用完整消息总线、依赖注入框架或主机单元测试。
- 不得因为时间紧而让业务代码直接写寄存器、直接修改其他模块的内部变量或无限等待硬件。

### 3.2 标准配置

适用于个人长期项目：

- 按第 4 章的职责分区组织目录和依赖。
- 驱动和服务支持多实例或明确的单实例封装。
- 使用端口接口隔离时间、日志、通信和并发原语。
- 对关键算法、通信解析和故障路径进行测试。
- 记录资源预算和平台适配差异。

### 3.3 完整配置

适用于复杂产品或多人协作：

- 维护正式的依赖图、接口契约、架构决策记录和变更审查。
- 引入持续集成、主机测试、硬件在环、故障注入和发布制品验证。
- 对实时性、内存、功耗、可靠性、安全和升级路径设定可测量指标。

## 4. 架构分区与依赖模型

嵌入式工程由产品主链和侧向公共能力共同组成。主链表达产品逻辑到硬件的依赖方向；侧向能力按需被主链中的一个或多个分区使用。

```text
产品主链：

app ──→ modules ──→ BSP ──→ drivers ──→ HAL ──→ hardware

侧向公共能力：

app / modules ──→ services ──→ BSP / drivers（硬件相关实现）
app / modules / services / BSP / drivers ──→ libraries
app / modules / services ──→ middleware ──→ drivers / HAL
```

箭头表示允许的编译期依赖方向。完成通知、回调、事件和数据可以在运行时向上流动，但下层模块不得 include 上层实现。目录用于表达职责和所有权，不要求每个分区都在所有项目中出现。

### 4.1 应用层（Application）

应用层负责产品入口、运行模式和用例编排，包括启动顺序、手动/自动切换、命令路由、任务组合和系统级降级策略。

应用层可以调用产品模块、共享服务、算法库、middleware 公共 API 和 BSP 公共 API。应用层不得直接访问寄存器、HAL 句柄、DMA 私有缓冲区或驱动内部状态。

典型内容：`main` 之外的应用入口、`control_manager`、命令处理、模式管理和系统状态编排。

### 4.2 产品模块（Modules / Domain Features）

产品模块负责运动、感知、导航、控制、通信行为等具体功能。每个模块封装自身状态机、产品规则和算法组合，并通过公共 API、事件或只读快照与其他模块协作。

产品模块可以使用服务、算法库、middleware 公共 API 和 BSP 公共 API。产品模块不得直接访问寄存器、HAL 句柄、生成代码内部对象或驱动私有状态。需要跨板复用或主机测试的模块 SHOULD 通过项目端口接口隔离 BSP；板卡绑定明确且规模较小的模块 MAY 直接依赖稳定的 BSP API。

典型内容：`motion_control`、`motion_manager`、`perception`、`navigation` 和协议行为状态机。

### 4.3 Domain 的使用条件

Domain 表示产品共享的数据模型、不变量和业务规则，是逻辑概念。产品规则通常由对应的产品模块拥有，不强制建立独立 `domain/` 目录。

同时满足以下条件时，可以建立独立 `domain/`：

- 同一套模型或规则被多个产品模块共同使用。
- 内容不依赖 BSP、驱动、HAL、RTOS、middleware 或具体通信方式。
- 生命周期独立于某个功能模块。
- 能够在主机环境中单独编译和测试。

独立 Domain 可以包含车辆状态模型、任务规则、路线模型和单位明确的领域值类型。PID、环形缓冲、CRC 等通用算法和数据结构归算法库；设备读取和板级配置归 BSP 或驱动。

### 4.4 服务（Services）

服务提供跨产品模块共享的系统能力，例如时间、错误、日志、诊断、事件、参数、持久化存储、看门狗管理和显示输出。

服务必须具有稳定 API 和明确生命周期，不包含具体产品流程和控制决策。纯算法不归服务：通用 PID、滤波器、CRC 和 FIFO 归算法库；与某个功能紧密绑定的算法归对应产品模块。

服务可以保持纯软件实现，也可以通过 BSP、驱动或 middleware 完成硬件相关功能。例如显示服务可以通过 BSP 显示接口输出，存储服务可以通过 Flash 驱动或文件系统 middleware 保存数据。

### 4.5 算法库与通用库（Libraries）

算法库提供无产品流程、无板卡绑定的可复用代码，例如 PID、滤波器、CRC、环形缓冲、数学运算、编码转换和容器。

库依赖标准 C、同级基础库或经过声明的最小平台能力，不依赖应用、产品模块、服务、BSP 或具体设备驱动。需要内存、时间或同步能力时，由调用者显式传入，或将对应实现归入 middleware。

### 4.6 中间件（Middleware，可选）

Middleware 表示具有独立生命周期和完整子系统性质的软件组件，例如 FreeRTOS、FatFs、LittleFS、LwIP、USB Device、LVGL 和第三方协议栈。

上层通过 middleware 公共 API 使用其能力；middleware 可以依赖驱动、HAL 和配置适配代码。厂商或第三方 middleware 保持其原始目录和代码风格，项目配置、适配器和封装代码遵循本文档。

未使用 middleware 的项目不创建空目录。单个算法文件、普通工具函数和简单设备驱动不归 middleware。

### 4.7 BSP（Board Support Package）

BSP 负责具体板卡的资源绑定和板级能力，包括引脚、电平、外设实例、DMA 通道、中断号、时钟、设备实例、初始化顺序和安全默认状态。

BSP 建立在设备驱动和 HAL 之上，向应用、产品模块和服务提供稳定的板级 API。BSP 可以作为组合根创建驱动句柄并注入配置，但不包含运动策略、路径规划、感知判断等产品规则。

典型 BSP API 表达板级能力，例如 `bsp_motor_set_speed()`、`bsp_encoder_read()`、`bsp_status_led_set()`。需要跨板复用的上层模块可以在 BSP API 之外再定义项目端口接口。

### 4.8 驱动与 HAL（Drivers / HAL）

驱动封装 MCU 外设或外部设备的操作协议，包括初始化、读写、启动/停止、DMA、中断回调、非阻塞状态和设备错误。通用设备驱动通过配置或总线端口获得硬件依赖；平台专用驱动可以直接使用 HAL 或寄存器。

驱动不知道产品模式、业务状态和应用流程。驱动通过返回值、回调或底层事件报告结果，不直接调用应用或产品模块。

HAL 包括 STM32 HAL/CMSIS、TI DriverLib、ESP-IDF/Arduino 底层 API、寄存器、启动文件和厂商生成代码。HAL 类型限制在驱动、BSP 和平台适配边界。

### 4.9 允许依赖矩阵

| 调用方 | 可直接依赖 | 不可直接依赖 |
| --- | --- | --- |
| 应用 | 产品模块、服务、库、middleware 公共 API、BSP 公共 API | HAL、寄存器、驱动私有状态 |
| 产品模块 | 其他模块公共 API、服务、库、middleware 公共 API、BSP 公共 API 或项目端口 | HAL、寄存器、生成代码、驱动私有状态 |
| 独立 Domain | 领域类型、纯算法库 | 应用、模块实现、服务实现、BSP、驱动、HAL、middleware |
| 服务 | 服务接口、库、middleware 公共 API、BSP 或必要的驱动公共 API | 具体应用流程、产品模块内部状态 |
| 库 | 标准 C、同级基础库、显式注入的最小能力 | 应用、产品模块、服务、BSP、具体驱动 |
| Middleware 适配代码 | middleware API、BSP、驱动、HAL | 产品规则和应用私有状态 |
| BSP | 驱动公共 API、HAL、生成代码、板级配置 | 应用流程和产品规则 |
| 驱动 | HAL、寄存器、注入的总线/GPIO/时间端口、底层库 | 应用、产品模块和产品策略 |
| 组合根 | 各分区公共接口和配置类型 | 各模块私有状态 |

### 4.10 依赖与通信规则

- 所有跨目录调用使用公共头文件，不 include 其他模块的私有头文件或 `.c` 文件。
- 运行时向上通知使用返回值、回调、事件、队列或只读快照。
- 共享数据具有唯一所有者；外部通过 API 读取或提交命令。
- 服务、库和 middleware 是按需依赖，不要求无语义的逐层转发。
- 端口接口用于隔离确实存在的平台替换、测试或多实现需求，不为简单调用机械增加函数指针层。
- 性能、启动时序或厂商限制要求偏离依赖矩阵时，按照第 19.5 节记录例外、影响和验证结果。

## 5. 目录与文件组织

推荐的通用仓库结构：

```text
project/
├── app/                    # 产品流程和系统编排
├── modules/                # 运动、感知、控制等产品功能
├── domain/                 # 跨模块共享的领域模型和规则（按需）
├── services/               # 时间、日志、错误、参数、协议等
├── libraries/              # PID、滤波、CRC、FIFO 等通用库
├── middleware/             # RTOS、文件系统、网络、GUI 等（按需）
├── bsp/                    # 板级资源和平台绑定
├── drivers/                # 外设/设备驱动
├── hal/                    # 平台封装或芯片相关适配
├── config/                 # 编译期和板级配置
├── tests/                  # 主机测试、替身和硬件测试说明
├── tools/                  # 生成、检查、烧录和分析脚本
├── docs/                   # 需求、硬件、架构和测试文档
├── .github/                # CI、Issue/PR 模板和自动化配置
├── CMakeLists.txt          # 或其他构建入口
├── README.md
└── LICENSE
```

小项目可以把上述目录合并为 `Core`、`Drivers`、`Users` 等少数目录，但必须在 README 或架构说明中写明实际映射。STM32CubeMX、TI SysConfig 等生成目录独立管理，用户代码放在可再生成的边界之外；ESP32 Arduino 项目也应把 Arduino API 访问集中在平台适配层。

### 5.1 STM32CubeMX 映射示例

```text
Core/Inc, Core/Src       → 生成的平台初始化和中断入口
Drivers/                 → CMSIS 与 STM32 HAL
User/App/                → 应用层
User/Modules/            → 产品功能模块
User/Domain/             → 共享领域模型（按需）
User/Services/           → 共享系统服务
User/Libraries/          → 算法和通用库
Middlewares/             → 厂商或第三方中间件（按需）
User/Bsp/                → 板级资源绑定
User/Drivers/            → 手写设备驱动
```

`main.c` 保持薄：调用生成初始化、系统组合入口和调度入口；用户业务不散落在 CubeMX 的 `USER CODE` 块中。不得为了追求目录完全一致移动生成文件，破坏再次生成能力。

### 5.2 MSPM0 SysConfig 映射示例

```text
ti_msp_dl_config.*       → 生成代码
platform/                → DriverLib 小型封装
bsp/<board>/             → 引脚、外设实例和中断绑定
drivers/                 → 可复用设备驱动
app/, modules/, services/ → 项目手写功能与共享能力
libraries/               → 平台无关算法和通用库
middleware/              → RTOS、文件系统或协议栈（按需）
```

### 5.3 ESP32 Arduino 映射示例

Arduino `setup()` 只进行平台和系统初始化，`loop()` 只调用应用调度入口。`Serial`、`Wire`、`SPI` 和 GPIO 类型限制在 BSP、驱动或平台适配代码中；FreeRTOS 类型限制在 middleware、调度和同步边界。使用 ESP32 自带 RTOS 能力时仍遵守第 13 章的任务和同步规则。

### 5.4 文件职责

- `README.md`：用途、目标硬件、工具链、构建、烧录、基本验证和已知限制。
- `config/`：编译期选项、板卡选择、功能开关和资源上限；不放业务流程。
- `bsp/`：板卡引脚、外设句柄、时钟和 IRQ 绑定；不放通用算法。
- `drivers/`：设备能力和硬件时序；不直接决定产品模式。
- `modules/`：产品功能、控制状态机和功能内算法组合。
- `domain/`：跨模块共享的稳定模型和产品规则；按第 4.3 节条件创建。
- `services/`：可被多个上层模块复用的系统能力；不反向调用具体业务。
- `libraries/`：平台无关算法和数据结构；不拥有产品流程和硬件资源。
- `middleware/`：具有独立生命周期的 RTOS、文件系统、网络、GUI 或第三方协议栈。
- `tests/`：测试输入、替身、断言和运行说明；不把临时调试代码混进生产模块。
- `docs/`：架构决策、硬件手册、接口契约和验证记录。
- `tools/`：可重复的生成、检查、打包和烧录辅助工具。

### 5.5 配置分层

配置按变化原因分开：

- 平台配置：芯片、时钟、外设实例和 DMA。
- 板级配置：引脚、电平、传感器型号和执行器连接。
- 产品配置：功能开关、能力组合和资源上限。
- 运行参数：PID、阈值、校准和用户设置。

运行参数不应与编译期宏混为一体。驱动公共头文件不保存“某个项目恰好使用”的速度和引脚值；这些值由 BSP 或配置对象注入。

### 5.6 构建边界

每个职责分区应成为清晰的构建目标或至少具有独立源文件列表。独立 Domain、纯算法库和声明为平台无关的产品模块应能在不链接 HAL 的情况下编译。平台选择通过构建系统选择 BSP、驱动或适配器源文件，不在每个模块内部散布平台条件编译。

## 6. 模块设计与 API 契约

### 6.1 模块边界

模块应具有单一、可命名的职责，拥有自己的状态和资源，并通过头文件暴露最小能力集合。判断一个模块是否应拆分时，检查：它是否有独立生命周期、独立测试方式、独立错误路径或独立平台替换需求。

### 6.2 接口形式

接口形式由模块类型、生命周期和实例数量决定：

```c
/* 多实例硬件驱动：句柄 + 配置 + 状态码 */
typedef struct motor_handle motor_handle_t;

motor_status_t motor_init(motor_handle_t *motor, const motor_config_t *config);
motor_status_t motor_set_speed(motor_handle_t *motor, int16_t speed);

/* 纯算法：不需要句柄时使用输入/输出参数 */
int32_t pid_compute(const pid_config_t *config, pid_state_t *state,
                    int32_t target, int32_t actual);

/* 系统唯一服务：隐藏内部实例，通过能力 API 访问 */
system_status_t system_time_ms(uint32_t *time_ms);
```

公共接口必须说明生命周期、所有权、阻塞性、超时、错误码、ISR/任务限制和线程安全。配置结构体用于初始化和板级绑定；运行时参数通过动作接口或明确的参数接口修改。

### 6.3 句柄、单实例和多实例

默认设计为多实例：调用者分配句柄，模块不依赖隐藏的全局状态。以下情况可以单实例：系统时钟、唯一看门狗、板载唯一 LED 等客观唯一资源。单实例也必须隐藏状态并提供 API，不能暴露可写全局对象。

### 6.4 依赖注入与适配器

需要时间、日志、GPIO、传输、存储、锁或队列的模块，优先通过配置结构体、端口接口或函数指针表注入依赖。这样可以：

- 让需要复用和主机测试的产品逻辑脱离芯片和 RTOS。
- 在主机测试中提供替身。
- 在 STM32、MSPM0、ESP32 之间替换实现。
- 在裸机和 RTOS 之间替换调度/同步实现。

只有在增加的抽象能够被替换、测试或复用时才引入；单个简单 GPIO 包装不应为了形式而建立多层接口。

### 6.5 标准驱动接口族

驱动按实际需要从下列接口族中选择，不要求实现所有函数：

```c
driver_status_t xxx_init(xxx_handle_t *handle, const xxx_config_t *config);
driver_status_t xxx_deinit(xxx_handle_t *handle);
driver_status_t xxx_start(xxx_handle_t *handle);
driver_status_t xxx_stop(xxx_handle_t *handle);
driver_status_t xxx_reset(xxx_handle_t *handle);
driver_status_t xxx_read(xxx_handle_t *handle, xxx_sample_t *sample);
driver_status_t xxx_write(xxx_handle_t *handle, const xxx_command_t *command);
void xxx_task(xxx_handle_t *handle);
void xxx_on_event_isr(xxx_handle_t *handle, xxx_irq_event_t event);
```

`init` 只建立可验证的初始状态；`start` 开始运行；`stop` 将输出置于安全状态；`deinit` 释放或解绑资源。简单驱动可以合并部分阶段，但契约仍需明确。

### 6.6 运行参数接口

动作语义使用具名函数，如 `motor_start()`、`camera_capture()`。同类型且数量较多的普通运行参数可以使用参数枚举，但必须保留类型和范围检查。

```c
typedef enum {
    MOTOR_PARAM_TARGET_SPEED,
    MOTOR_PARAM_ACCELERATION,
    MOTOR_PARAM_CURRENT_LIMIT,
} motor_param_t;

motor_status_t motor_set_parameter(motor_handle_t *motor,
                                   motor_param_t parameter,
                                   int32_t value);
```

不同类型、带复杂副作用或需要原子更新的一组参数，应使用配置对象和 `apply` 接口，不能用无类型的 `void *` 或万能整数接口。

### 6.7 数据共享方式

| 方式 | 适用场景 | 关键约束 |
| --- | --- | --- |
| 直接函数调用 | 同步、一对一、调用链明确 | 不形成反向依赖 |
| Getter/快照 | 一个生产者、多个只读消费者 | 说明一致性和时间戳 |
| 命令接口 | 消费者要求生产者执行动作 | 不暴露内部字段 |
| 回调 | 一个明确消费者的异步完成 | 说明执行上下文和时限 |
| 队列 | 跨任务、有缓冲需求 | 容量和满队列策略明确 |
| 发布订阅 | 多消费者、动态组合 | 生命周期和丢失策略明确 |

返回内部可写指针通常违反所有权。需要高效读取大型数据时，可以返回 `const` 视图或双缓冲快照，但必须说明有效期和并发规则。

### 6.8 系统组合根

所有实例创建、平台端口绑定和模块装配集中在一个组合根，例如 `system.c` 或 `app_composition.c`。驱动本身不 include 组合根头文件。

```c
/* system.c */
static motor_handle_t left_motor;
static encoder_handle_t left_encoder;

static const motor_config_t left_motor_config = {
    .pwm_channel = BSP_PWM_LEFT,
    .direction_pin = BSP_MOTOR_LEFT_DIRECTION,
};

system_status_t system_init(void)
{
    motor_status_t motor_status;
    encoder_status_t encoder_status;

    motor_status = motor_init(&left_motor, &left_motor_config);
    if (motor_status != MOTOR_STATUS_OK) {
        return system_status_from_motor(motor_status);
    }

    encoder_status = encoder_init(&left_encoder, &left_encoder_config);
    if (encoder_status != ENCODER_STATUS_OK) {
        return system_status_from_encoder(encoder_status);
    }

    return SYSTEM_STATUS_OK;
}
```

组合根负责把句柄或端口传入需要对应能力的模块。个人小项目可以使用受控 getter，但 getter 只返回只读或受控句柄，并限制在明确的资源访问边界。

### 6.9 模块独立性检查

- 模块 `.c` 第一个 include 是自身头文件。
- 不 include `main.h`、项目总头文件或应用层头文件。
- 不硬编码板级引脚和外设实例。
- 状态由句柄或内部 `static` 对象拥有。
- 所有外部访问经过公共 API。
- 模块可在最小测试构建中独立编译。
- 多实例需求明确；单实例有客观理由。
- 平台专用内容位于端口或适配器实现。

## 7. 生命周期与初始化

初始化顺序必须满足“被依赖者先初始化”：

```text
复位/时钟
  → GPIO / DMA / 通信外设
    → BSP 资源
      → 驱动
        → 服务
          → 领域对象
            → 应用任务
```

每个初始化 API 必须说明：依赖的前置条件、是否可重复调用、失败后的对象状态、是否需要反初始化以及启动后由谁调度。平台初始化、驱动初始化和业务启动分开；不要在驱动初始化中隐式开启尚未配置的应用行为。

### 7.1 初始化失败与降级

初始化链遇到失败时，停止启动依赖该能力的模块，并选择安全停机、有限重试、降级运行或诊断模式。不能忽略错误继续启动，再由空句柄或无效硬件状态触发更难定位的故障。

每个可选模块在产品配置中明确是否允许缺失。例如显示模块失败可以降级为串口诊断；电机反馈失败通常必须禁止运动。降级策略属于应用层，不应写死在驱动中。

### 7.2 幂等与重复初始化

每个模块明确重复调用 `init`、`start`、`stop` 和 `deinit` 的行为。推荐 `stop` 和安全动作幂等；重复 `init` 可以返回 `ALREADY_INITIALIZED`，也可以在完全停止后重建，但不能隐式泄漏资源或重复注册中断。

### 7.3 中断启用与关闭顺序

句柄、缓冲区、回调和状态机全部就绪后再启用中断。初始化期间产生的待处理中断必须在启用前清除。关闭顺序相反：先禁止新事件，再停止 DMA/外设，最后释放或清空状态。

```c
driver_status_t uart_start(uart_handle_t *uart)
{
    platform_irq_disable(uart->irq);
    platform_irq_clear_pending(uart->irq);
    uart_reset_fifo(uart);
    uart_start_rx_dma(uart);
    platform_irq_enable(uart->irq);
    return DRIVER_STATUS_OK;
}
```

## 8. 状态机模式

有等待、重试、超时、分阶段操作或故障恢复的模块必须优先采用非阻塞状态机。

状态机至少定义：

- 状态集合和初始状态。
- 外部事件和内部条件。
- 状态转移。
- 每个状态的进入动作、执行动作和退出动作。
- 超时、非法事件和错误恢复。
- 完成、失败和取消的通知方式。

```c
typedef enum {
    SENSOR_STATE_IDLE,
    SENSOR_STATE_STARTING,
    SENSOR_STATE_WAITING,
    SENSOR_STATE_READY,
    SENSOR_STATE_FAULT,
} sensor_state_t;

void sensor_task(sensor_handle_t *sensor)
{
    switch (sensor->state) {
    case SENSOR_STATE_IDLE:
        sensor_start_conversion(sensor);
        sensor->deadline = time_after_ms(20U);
        sensor->state = SENSOR_STATE_WAITING;
        break;
    case SENSOR_STATE_WAITING:
        if (sensor_conversion_done(sensor)) {
            sensor_read_result(sensor);
            sensor->state = SENSOR_STATE_READY;
        } else if (time_expired(sensor->deadline)) {
            sensor_report_timeout(sensor);
            sensor->state = SENSOR_STATE_FAULT;
        }
        break;
    case SENSOR_STATE_READY:
        sensor_publish(sensor);
        sensor->state = SENSOR_STATE_IDLE;
        break;
    case SENSOR_STATE_STARTING:
    case SENSOR_STATE_FAULT:
        sensor_recover(sensor);
        sensor->state = SENSOR_STATE_IDLE;
        break;
    default:
        sensor->state = SENSOR_STATE_FAULT;
        break;
    }
}
```

状态机每次调用只完成有限工作，不在状态内部无限等待；超时和非法状态必须有确定结果。

## 9. 事件驱动与消息传递

### 9.1 事件模型

事件描述已经发生的领域或设备事实，包含来源、类型、可选数据和时间戳。寄存器状态由驱动转换成稳定事件，生产者不直接调用消费者的内部函数。

裸机可以使用事件位、固定数组或环形队列；RTOS 可以映射到队列、事件组或任务通知。上层只依赖项目事件接口，不依赖具体 RTOS 类型。

### 9.2 发布-订阅和消息总线

发布-订阅适合一个事件有多个消费者、生产者和消费者生命周期不同或需要替换消费者的场景。使用时必须规定：

- topic/事件 ID 的所有权。
- 消息大小、队列深度和溢出策略。
- 消息是复制、引用还是借用。
- 消费顺序、优先级和丢失容忍度。
- 订阅者注销和生命周期。

简单的一对一调用优先使用函数或直接接口，不为单个生产者/消费者引入全局消息总线。

### 9.3 生产者-消费者与 FIFO

UART DMA、传感器采集和协议解析通常采用：

```text
硬件 → DMA/ISR → FIFO → 解析任务 → 领域事件 → 应用
```

FIFO 规定单写者/单读者优先；读写索引、满/空条件、溢出策略和临界区必须明确。DMA 缓冲区的所有权在回调完成前不转移；消费者不得直接修改生产者仍在使用的缓冲区。

### 9.4 事件结构和队列接口

```c
typedef enum {
    EVENT_SENSOR_SAMPLE_READY,
    EVENT_MOTOR_FAULT,
    EVENT_COMMAND_RECEIVED,
} event_type_t;

typedef struct {
    event_type_t type;
    uint32_t timestamp_ms;
    uint16_t source;
    event_payload_t payload;
} event_t;

event_status_t event_publish(const event_t *event);
event_status_t event_try_receive(event_t *event);
```

事件载荷默认小且定长。大型数据通过对象池句柄、只读快照或引用计数对象传递，并明确释放责任。禁止把栈对象指针或会被 DMA 继续覆盖的缓冲区投递到异步队列。

### 9.5 队列满和事件合并

队列满必须选择显式策略：

- 控制命令和故障：保留高优先级事件，必要时触发安全状态。
- 连续传感器值：可以只保留最新样本并累计丢弃计数。
- 协议字节流：不得静默丢弃，应复位帧解析并上报溢出。
- 日志：允许按等级丢弃，但要记录丢弃数量。

周期性“刷新”事件可以用事件位合并，不能让相同事件无限堆积。队列深度根据峰值生产速率、最大消费延迟和可容忍突发量计算。

### 9.6 回调规则

回调适合一个明确消费者的完成或错误通知。注册时说明回调上下文、生命周期和是否可在 ISR 执行。驱动不得在持锁或临界区中调用未知回调；若回调来自 ISR，名称或接口文档必须明确 `_isr` 语义。

## 10. 端口-适配器

端口描述上层所需的能力，适配器实现平台细节。典型端口包括：

- 时间和延时。
- GPIO、PWM、ADC、传感器。
- 串口、SPI、I2C 和网络。
- 日志和诊断。
- 非易失存储。
- 临界区、锁、队列和事件。

```c
typedef struct {
    uint32_t (*now_ms)(void *context);
    void (*sleep_until)(void *context, uint32_t deadline_ms);
    void *context;
} time_port_t;
```

裸机适配器可以读取系统 tick 并返回主循环；RTOS 适配器可以映射到系统时钟和任务延时。端口接口不能泄露 `HAL_HandleTypeDef`、FreeRTOS `QueueHandle_t` 或 Arduino 对象。

## 11. 组件化与接口表

当需要替换实现、多实例、平台适配或测试替身时，使用句柄和函数指针表：

```c
typedef struct {
    int32_t (*read)(void *context, uint8_t *data, uint16_t length);
    int32_t (*write)(void *context, const uint8_t *data, uint16_t length);
    void *context;
} transport_port_t;
```

规则：

- 函数指针表在初始化后默认为只读。
- `context` 的生命周期必须长于所有调用。
- 缺失能力通过显式错误返回，不调用空指针。
- 接口表用于可替换能力，不用于隐藏普通函数调用。
- 回调执行上下文、阻塞性和线程安全必须写入接口契约。

### 11.1 模式选型表

设计模式用于解决已经存在的变化、并发或复用问题，不作为“专业程度”的装饰。选择前先回答：什么会变化、谁拥有状态、调用是同步还是异步、资源成本是否可接受。

| 问题 | 首选模式 | 不必使用的情况 |
| --- | --- | --- |
| 分阶段、等待和超时 | 状态机 | 一次同步计算即可完成 |
| 替换硬件或平台实现 | 端口-适配器/策略 | 永远不会替换的局部函数 |
| 一个事件通知多个模块 | 发布-订阅/观察者 | 明确的一对一调用 |
| 跨任务传递动作 | 命令 + 有界队列 | 同一调用栈内立即执行 |
| 异步设备独占资源 | Active Object/设备任务 | 裸机单调用者简单设备 |
| 创建固定类型实例 | 工厂/组合根 | 只有一个静态实例 |
| 持久化与领域隔离 | Repository/存储端口 | 单个驱动寄存器读写 |
| 可替换算法 | 策略模式 | 只有一个稳定算法 |

### 11.2 策略模式

策略模式适合控制算法、滤波器、路径选择或校验方法需要替换的场景。C 中使用函数指针表和上下文：

```c
typedef struct {
    int32_t (*compute)(void *context, int32_t target, int32_t actual);
    void (*reset)(void *context);
    void *context;
} controller_strategy_t;

typedef struct {
    controller_strategy_t controller;
    motor_port_t motor;
} motion_control_t;
```

规则：

- 在初始化时绑定策略，运行期不随意改写函数表。
- 策略输入输出使用领域类型，不泄露驱动句柄。
- 不同策略保持相同单位、范围和失败语义。
- 只有一个简单算法且没有测试替换需求时，直接函数调用更清楚。

### 11.3 命令模式

命令对象适合把“请求执行动作”从产生者传递给拥有资源的任务。

```c
typedef enum {
    MOTOR_COMMAND_SET_SPEED,
    MOTOR_COMMAND_STOP,
    MOTOR_COMMAND_CLEAR_FAULT,
} motor_command_type_t;

typedef struct {
    motor_command_type_t type;
    union {
        int16_t speed;
    } parameter;
} motor_command_t;
```

命令队列必须规定：同类命令是否覆盖、停止命令是否具有优先权、队列满时如何保证安全动作、命令过期后是否仍执行。紧急停止不应因为普通命令队列已满而丢失，可以使用专用高优先级事件或硬件安全路径。

### 11.4 Active Object / 设备拥有者

RTOS 中可以让一个任务独占 I2C、SPI、文件系统或复杂设备，其他任务通过命令队列请求服务。设备拥有者串行执行事务，因此调用方无需直接锁底层句柄。

```text
传感器任务 ─┐
显示任务 ───┼→ I2C 请求队列 → I2C Owner Task → HAL/DMA
参数任务 ───┘                       ↓
                         完成事件/响应队列
```

适用条件：事务可能阻塞、调用者较多、总线需要统一超时恢复。代价是队列、任务栈、调度延迟和异步接口复杂度。裸机或只有一个调用者时，普通总线服务加状态机通常足够。

### 11.5 Repository / 持久化端口

产品模块和独立 Domain 不直接读写 Flash 地址、NVS key 或文件路径，通过语义接口保存配置：

```c
typedef struct {
    settings_status_t (*load)(void *context, system_settings_t *settings);
    settings_status_t (*save)(void *context, const system_settings_t *settings);
    void *context;
} settings_repository_t;
```

存储适配器负责版本、校验、磨损、掉电一致性和平台 API。产品模块只感知完整设置对象是否加载或保存成功。对于只有一个校准值的小项目，可以使用简单存储服务，不需要建立通用数据库式 Repository。

### 11.6 双缓冲与快照

高速生产者、低速消费者共享一组数据时，可以使用双缓冲：生产者写非活动缓冲，完成后原子交换活动索引；消费者获得只读快照。规则：

- 交换前生产者必须完成整帧写入。
- 消费者使用期间缓冲不能被重新作为写缓冲，或必须允许覆盖旧快照。
- 数据包含序列号和时间戳，用于识别跳帧和过期。
- 多消费者需要引用计数、三缓冲或复制，不能假设所有消费者同时完成。

### 11.7 状态模式与分层状态机

状态数量较少时，一个 `switch` 最容易审查。状态超过约十个、存在明确父状态或多个正交区域时，可以拆分状态处理函数或使用层次状态机。不要仅为了消除 `switch` 使用大量函数指针，使转移关系难以搜索。

分层状态机需要明确：父状态处理哪些公共事件、未处理事件是否向父级传播、进入/退出顺序，以及历史状态是否保留。生成状态机代码时，模型文件和生成器版本必须进入仓库。

### 11.8 观察者与发布-订阅区别

观察者通常同步调用已注册回调，适合少量、确定执行时间的订阅者；发布-订阅通常经过事件队列或 broker，适合异步和多任务。同步观察者必须防止：

- 订阅者在回调中注销自己导致遍历失效。
- 某个回调阻塞整个发布者。
- 回调反向调用发布者形成递归。
- ISR 发布时调用不具备 ISR 安全性的订阅者。

### 11.9 工厂与组合根

C 项目通常不需要通用反射式工厂。实例数量和类型在编译期已知时，由组合根静态创建最清楚。只有产品配置需要选择多个实现之一时，才使用小型工厂返回端口或句柄。

```c
const transport_port_t *transport_factory_create(transport_type_t type)
{
    switch (type) {
    case TRANSPORT_TYPE_UART:
        return uart_transport_port();
    case TRANSPORT_TYPE_USB:
        return usb_transport_port();
    default:
        return NULL;
    }
}
```

工厂不动态分配对象，不隐藏复杂初始化失败；创建后的所有权和生命周期仍由组合根管理。

### 11.10 常见架构反模式

#### 万能 `main.h`

所有模块 include 一个聚合头，造成隐式依赖、循环包含和平台泄漏。替代方式是每个模块 include 自己直接使用的最小接口。

#### 全局可写状态

应用、ISR 和驱动直接读写同一个结构体，无法判断所有权和同步。替代方式是模块 API、快照、事件和单写者规则。

#### 上帝模块

`system.c`、`manager.c` 或 `control.c` 同时包含初始化、状态机、协议、算法和错误处理。组合根只负责装配；业务编排、服务和驱动分别归层。

#### 回调地狱

驱动回调直接调用业务，业务再调用另一个驱动，最终形成不可控 ISR 调用链。回调应转换成事件，复杂流程由显式状态机推进。

#### 无界队列和无界重试

为了“绝不丢数据”不断扩大缓冲或无限重试，最终耗尽内存或阻塞系统。所有队列、重试和等待都必须有上限与降级策略。

#### 每个模块一个任务

任务数量随文件数量增长，浪费栈并制造同步问题。任务代表独立调度和资源所有权，不代表源代码模块。

#### 伪抽象层

只把 HAL 函数一对一改名，却仍暴露相同句柄和语义，增加跳转而没有隔离变化。有效适配器应提供项目需要的能力和稳定契约。

#### 服务定位器滥用

任意模块通过 `system_get_xxx()` 获取任何设备，依赖图再次变成隐式全局网络。组合根注入依赖；仅在小项目或框架入口使用受控 getter。

### 11.11 模式引入检查

引入新的设计模式前记录：

- 当前具体问题和变化来源。
- 不使用模式时的真实成本。
- 新增 RAM、Flash、栈、队列和运行时开销。
- 调试路径是否更清晰。
- 最小项目能否裁剪。
- 主机测试或平台替换是否因此变得可行。
- 将来移除该模式需要修改哪些接口。

## 12. 裸机运行模型

### 12.1 主循环

主循环负责调度有限、非阻塞的任务；不得通过 `HAL_Delay()` 或无限等待保证业务时序。周期任务由 tick、时间戳或事件触发，输入型消费者通常“有数据就处理”，输出型任务按速率限流。

```c
int main(void)
{
    platform_init();
    system_init();
    interrupts_enable();

    while (1) {
        event_dispatch();
        sensor_task();
        control_task();
        communication_task();
        system_health_update();

        if (system_health_all_critical_tasks_ok()) {
            watchdog_feed();
        }
    }
}
```

### 12.2 ISR 与 DMA

ISR 允许读写硬件状态、清除中断、搬运数据、更新计数器和置事件；禁止复杂业务、循环等待、动态内存、日志格式化和不可证明的浮点路径。DMA 完成、错误和空闲事件通过回调或事件送到任务层处理。

中断优先级依据控制时序、数据完整性和可抢占性决定，不按外设名称机械排序。必须避免长时间关闭中断，并测量关键 ISR 的最坏执行时间。

### 12.3 临界区与原子性

优先采用单写者/单读者和不可变快照减少共享；需要保护复合操作时使用平台临界区。临界区必须尽可能短，不在其中调用阻塞函数、日志、驱动长事务或不可控回调。`volatile` 只解决编译器可见性，不保证复合读改写原子性。

### 12.4 调度机制

裸机调度可以采用时间戳、事件位或固定周期计数器。推荐统一单调时钟和任务描述，不让每个模块各自访问不同定时器。

```c
typedef struct {
    uint32_t period_ms;
    uint32_t next_run_ms;
    void (*run)(void *context);
    void *context;
} periodic_task_t;

static void scheduler_run(periodic_task_t *tasks, size_t task_count, uint32_t now_ms)
{
    for (size_t index = 0U; index < task_count; index++) {
        if (time_reached(now_ms, tasks[index].next_run_ms)) {
            tasks[index].next_run_ms += tasks[index].period_ms;
            tasks[index].run(tasks[index].context);
        }
    }
}
```

时间比较必须正确处理 tick 回绕，统一使用时间工具函数。任务执行超时不能靠“下一轮再说”掩盖，应测量并上报 deadline miss。

### 12.5 Task 分类

| 类型 | 示例 | 调度方式 |
| --- | --- | --- |
| 事件消费者 | UART 解析、DMA 完成、传感器 FIFO | 有数据立即处理，单次限制工作量 |
| 固定周期控制 | PID、姿态更新、按键消抖 | 单调时钟或硬件周期事件 |
| 速率受限输出 | OLED、遥测、日志刷新 | 按最大输出频率运行 |
| 后台维护 | 参数保存、诊断、统计 | 低优先级、分片执行 |

输入消费者不应额外等待低频 tick，避免 FIFO 堵塞；固定周期算法也不能依赖主循环“碰巧足够快”。每次 task 处理的最大事件数应有限，防止高流量消费者饿死其他任务。

### 12.6 Tick 标志、计数和丢周期

简单项目可以由 ISR 置位标志、主循环读取并清除。如果事件不能丢失，使用计数器或队列，不能使用单 bit 标志。

```c
static volatile uint32_t control_pending_count;

void control_timer_on_update_isr(void)
{
    if (control_pending_count < CONTROL_PENDING_MAX) {
        control_pending_count++;
    }
}

void control_task(void)
{
    uint32_t pending = critical_exchange_u32(&control_pending_count, 0U);

    while (pending > 0U) {
        control_step();
        pending--;
    }
}
```

不允许补跑的控制算法只处理最新采样并记录错过周期。事件计数和最新值覆盖根据控制时序与数据语义选择。

### 12.7 非阻塞的精确定义

非阻塞不等于“通常很快”。非阻塞 API 在一次调用中完成有限工作，不等待外部状态，并在可说明的上限内返回。异步操作通过状态、事件或回调通知完成。初始化阶段允许经过说明的短阻塞延时；运行阶段阻塞必须进入实时预算。

### 12.8 看门狗与任务健康

- 硬件看门狗由系统监督点统一喂，不由每个 task 自行喂。
- 只有关键任务均在本周期报告健康时才喂狗。
- 保存并上报复位原因，区分上电、看门狗、软件和掉电复位。
- 软件心跳允许合理抖动，不能因一次延迟立即复位。
- 调试版本不能长期关闭看门狗而让发布路径从未验证。

## 13. RTOS 运行模型

RTOS 提供调度和同步能力。声明为平台无关的产品模块和独立 Domain 不包含 RTOS 类型。任务边界按责任、时序和资源所有权划分；源码模块与 RTOS 任务不存在一一对应关系。

每个任务应能说明：

- 责任和输入事件。
- 优先级依据。
- 栈大小来源。
- 最大阻塞时间和最坏执行时间。
- 队列/通知容量。
- 共享资源和锁顺序。
- 超时和故障恢复。

必须识别优先级反转、死锁、队列满、任务饥饿和栈溢出风险。互斥锁只保护明确的共享资源，不用全局大锁包住整段业务。

### 13.1 任务划分

独立实时周期、可能阻塞的 I/O、故障隔离或明确生产者/消费者边界支持拆成独立任务。“这是一个模块”本身不足以创建任务。多个短小、同优先级、同周期模块可以由一个任务依次调度。

### 13.2 同步原语选择

| 需求 | 推荐原语 | 不推荐替代 |
| --- | --- | --- |
| ISR 唤醒一个任务 | 任务通知/二值信号 | 轮询共享布尔值 |
| 传递有序数据 | 有界队列/流缓冲 | 多个无所有权全局变量 |
| 保护共享资源 | 带优先级继承的互斥锁 | 长时间关中断 |
| 计数资源或事件 | 计数信号量 | 会丢事件的单 bit |
| 多条件状态 | 事件组或一致快照 | 多个无原子一致性的标志 |

ISR 只能调用 RTOS 提供的 ISR-safe API，并按要求请求上下文切换。普通互斥锁不能在 ISR 使用。

### 13.3 锁与死锁

共享资源规定唯一锁；多个锁存在嵌套时定义全局获取顺序。持锁期间不得等待队列、执行长 I/O、调用未知回调或睡眠。能通过消息所有权、单任务拥有设备或不可变快照解决的问题，不增加锁。

### 13.4 优先级和实时性

优先级按 deadline、周期、阻塞链和故障后果设置，不按“模块重要程度”主观排序。高优先级任务不得依赖低优先级任务的普通队列处理才能释放关键资源。必须观察响应时间、抖动、上下文切换和 CPU 空闲率。

### 13.5 栈、堆和任务退出

任务栈初值来自调用深度、局部数组、库函数和 FPU 上下文估计，再用高水位或填充检查验证。禁止只因栈溢出就盲目加倍。RTOS 对象优先静态创建；动态创建限定在启动阶段并检查失败。

永久任务通常不自行退出；确需退出时先停止事件来源、归还所有权、注销订阅并释放由它创建的资源。禁止删除仍被其他对象引用的任务或队列。

### 13.6 裸机/RTOS 统一端口

```c
typedef struct {
    bool (*post)(void *queue, const event_t *event, uint32_t timeout_ms);
    bool (*post_isr)(void *queue, const event_t *event, bool *should_yield);
    bool (*receive)(void *queue, event_t *event, uint32_t timeout_ms);
} event_queue_port_t;
```

产品模块通常不直接持有 RTOS 队列类型；应用、服务或调度适配代码负责事件传递。操作系统抽象只覆盖项目实际使用且需要替换的能力。

## 14. 通信架构

通信模块分为传输、帧处理和领域处理：

```text
硬件/DMA → 传输缓冲 → 帧边界检测 → 协议解析 → 命令/数据模型 → 产品模块
```

- 传输层只负责字节可靠搬运和错误。
- 帧层负责长度、校验、转义、版本和超时。
- 协议层负责命令语义和响应。
- 产品模块决定命令是否允许以及执行什么产品行为。
- 接收、解析和执行可异步，禁止在 ISR 中完整解析复杂协议。
- 缓冲区大小、溢出策略、最大帧长和超时必须明确。

### 14.1 UART RX：DMA、空闲检测与环形缓冲

推荐数据流：

```text
UART → DMA 临时缓冲 → IDLE/RX Timeout/定期余量检测
     → RX 环形缓冲 → 帧解析器 → 协议消息
```

STM32 可以使用 IDLE 或接收超时事件；没有硬件空闲检测的平台可以周期读取 DMA 剩余量，在连续两次无变化且已有数据时判定本批接收结束。平台差异只存在于 UART 适配器，环形缓冲和解析器保持通用。

环形缓冲至少提供 `init`、`push`、`pop`、`available`、`free`、`clear` 和溢出计数。保留一个空位是简单可靠的满/空判定方案：

```c
typedef struct {
    uint8_t *data;
    uint16_t capacity;
    volatile uint16_t read_index;
    volatile uint16_t write_index;
    volatile uint32_t overflow_count;
} ring_buffer_t;

bool ring_buffer_push_isr(ring_buffer_t *buffer, uint8_t value)
{
    uint16_t next = (uint16_t)((buffer->write_index + 1U) % buffer->capacity);

    if (next == buffer->read_index) {
        buffer->overflow_count++;
        return false;
    }

    buffer->data[buffer->write_index] = value;
    buffer->write_index = next;
    return true;
}
```

生产者只写 `write_index`，消费者只写 `read_index`。如果目标架构不能保证索引宽度的原子访问，或存在缓存/多核，必须增加平台同步。ISR 搬运量过大时采用 DMA 双缓冲或零拷贝描述符，不能在高优先级 ISR 中逐字节复制无限数据。

### 14.2 UART TX：队列与 DMA 链式发送

应用把完整消息或字节写入有界 TX 队列；若发送空闲，驱动启动一批 DMA；DMA 完成 ISR 只更新读位置并触发下一批。必须明确：

- 写入接口是全有或全无，还是允许部分写入。
- 多调用者的消息是否需要原子入队。
- 队列满时返回 `BUSY`、等待有限时间还是丢弃低优先级消息。
- DMA 正在读取的内存不得被调用者修改。
- 发送错误后如何丢弃、重试或重新同步。

### 14.3 帧解析状态机

解析器逐字节或逐块消费，不依赖一次 DMA 回调恰好得到完整帧。典型状态包括等待帧头、读取头部、读取载荷、读取校验和、完成和丢弃。

```text
WAIT_SYNC → READ_HEADER → READ_PAYLOAD → READ_CHECKSUM → COMPLETE
     ↑              任意长度/校验/超时错误 → DISCARD ─────┘
```

解析规则：最大帧长在分配或复制前检查；超时后复位到同步状态；校验失败累计诊断计数；未知命令由协议层返回明确错误，不由传输层决定业务响应。

### 14.4 SPI 与 I2C 事务

总线由一个驱动或服务拥有，多个设备通过事务对象提交访问。事务包含设备、操作、地址、缓冲区、长度、超时和完成通知。不得由不同模块直接持有同一个 HAL 总线句柄并各自启动 DMA。

I2C/SPI 错误恢复按平台能力执行：停止事务、清错误、复位外设、必要时恢复总线，再让上层决定重试。重试必须有限且不能在 ISR 内循环完成。

### 14.5 协议版本和兼容性

持久化或跨设备协议 SHOULD 含版本字段。新增可选字段保持旧解析器可跳过；改变字段语义或字节布局时升协议主版本。协议结构不能直接序列化编译器结构体，必须显式处理字节序、长度和校验。

## 15. 错误处理与恢复

错误至少区分参数、状态、超时、传输、硬件和资源错误。模块通过返回状态、错误事件或错误对象传播，不静默吞掉失败。

错误处理分为三层：

1. **检测/传输**：模块记录来源和错误码，不决定产品策略。
2. **上报/诊断**：服务层记录、显示或发送错误，不直接修改驱动内部状态。
3. **处理/恢复**：应用或系统策略决定重试、复位、降级、停机或继续运行。

恢复动作必须幂等；重试次数、退避、超时和最终失败状态必须有上限。错误处理本身不得造成循环重试、队列无限增长或看门狗失效。

### 15.1 错误对象

```c
typedef enum {
    ERROR_SEVERITY_INFO,
    ERROR_SEVERITY_WARNING,
    ERROR_SEVERITY_RECOVERABLE,
    ERROR_SEVERITY_FATAL,
} error_severity_t;

typedef struct {
    uint16_t source;
    uint16_t code;
    error_severity_t severity;
    uint32_t timestamp_ms;
    uint32_t context;
} error_event_t;
```

错误来源 ID 由项目集中注册，错误码由模块定义。不要用一个 32 位位图假设错误源永远少于 32 个；最小项目可以使用位图，规模扩大时切换到固定事件队列和每源状态表。

### 15.2 错误传输

同步错误首先通过函数返回值交给直接调用者；异步硬件错误通过错误事件传输。驱动可以记录寄存器快照等诊断上下文，但不直接操作 OLED、蓝牙或业务状态。

错误队列必须防止相同持续故障无限重复入队。常用策略是每个来源维护当前状态和 `queued` 标志；状态变化或经过限流周期后才再次上报。

### 15.3 上报与诊断

上报层把错误转换为日志、屏显、遥测或复位记录。格式化和 I/O 在任务上下文完成。资源不足时优先保留致命错误和首次错误，后续重复只增加计数。

### 15.4 恢复策略

| 故障 | 常见策略 |
| --- | --- |
| 短暂总线错误 | 清错误、有限重试、退避 |
| 传感器持续失联 | 重新初始化、使用降级数据、禁止相关功能 |
| 电机/执行器异常 | 立即安全输出，等待应用确认恢复 |
| 参数或状态错误 | 拒绝操作、记录上下文，不盲目复位硬件 |
| 内存/栈/内部不变量 | 保存最小诊断并安全复位或停机 |

ISR 可完成硬件必须立即执行的安全动作和最小复位；完整恢复由任务状态机处理。错误清除只在故障条件真正消失、恢复验证通过后执行。

### 15.5 故障状态机

关键设备推荐使用 `NORMAL → DEGRADED → RECOVERING → NORMAL/FAILED` 状态机。恢复次数和时间窗口有上限；超过上限进入 `FAILED`，等待人工操作、系统重启或更高层策略，禁止无限重初始化。

## 16. 内存、资源与实时性

默认优先使用静态分配、调用者提供的缓冲区和固定大小对象池。动态内存只有在平台、生命周期、最大占用、碎片风险、失败处理和释放责任都明确时才可作为例外。

每个标准项目至少记录关键资源：

| 资源 | 必须说明的内容 |
| --- | --- |
| Flash | 固件、常量、引导和升级空间 |
| RAM | 全局、堆、栈、DMA 和缓存 |
| 栈 | 每个任务或关键调用链的上限 |
| CPU | 周期、最坏执行时间和中断占用 |
| 通信 | 速率、最大帧、FIFO 深度和丢包策略 |
| 功耗 | 睡眠、唤醒和高负载状态（适用时） |

控制输出必须在最终驱动边界限幅；PID 等算法需要积分饱和和异常输入保护。看门狗在统一的位置喂狗，并在复位后记录复位原因。

### 16.1 静态内存布局

长期对象在组合根或模块中静态分配；大型 DMA 缓冲区根据平台要求放入正确的内存区和对齐边界。链接脚本中的 RAM 区域、栈、堆、DMA 不可访问区和保留区必须与芯片实际一致。

### 16.2 对象池

需要运行期创建有限数量消息、事务或帧时，使用固定对象池：

- 容量由峰值并发需求和安全余量决定。
- 获取失败返回明确错误，不能返回未初始化对象。
- 对象归还前清除所有权和链表状态。
- 调试版本检测重复释放、越界和池泄漏。
- ISR 使用的池操作必须有确定时间且并发安全。

### 16.3 动态内存例外

ESP32 网络栈、文件系统或第三方组件可能依赖堆。项目允许保留第三方内部动态分配，但应用代码应限制：

1. 尽量只在启动阶段分配。
2. 记录最大堆占用和最低剩余堆。
3. 检查每次可失败分配。
4. 禁止 ISR 和硬实时控制路径分配。
5. 长时间压力测试碎片和失败恢复。

### 16.4 实时预算表

| 执行单元 | 周期/触发 | Deadline | WCET | 抖动 | 超时动作 |
| --- | --- | --- | --- | --- | --- |
| 控制环 | 5 ms | 5 ms | 待测 | 待测 | 安全输出/记录丢周期 |
| UART RX | DMA/IDLE | FIFO 溢出前 | 待测 | 不适用 | 复位解析器 |
| OLED | 50 ms | 200 ms | 待测 | 可容忍 | 跳过本帧 |

数字由项目测量填写，规范不硬编码“所有控制环必须多少 Hz”。周期来自系统带宽、数据到达率和用户感知要求，并保留 CPU 余量。

### 16.5 安全输出与限幅

- 执行器初始化、停止、错误和看门狗复位前均有定义好的安全输出。
- 限幅在最终输出边界执行，上层重复校验属于附加保护。
- PID 包含积分抗饱和、输出限幅和异常采样处理。
- 传感器超范围、NaN、校验失败或过期样本不得直接进入控制输出。
- 紧急停机路径不依赖普通任务队列有空位。

## 17. 供应商代码与平台迁移

### 17.1 生成代码

STM32CubeMX、TI SysConfig 和其他配置工具生成的文件默认隔离且禁止手改。工具配置、版本和生成命令必须可追溯；手写实现放在用户目录、BSP 或适配层。若工具无法避免修改生成文件，必须记录生成后需要重新应用的补丁或人工步骤。

### 17.2 平台差异

平台差异集中在 HAL、BSP、驱动和端口适配器。独立 Domain、算法库和声明为平台无关的产品模块不使用平台宏控制核心逻辑。`#ifdef` 优先出现在平台边界，嵌套不超过两层；同一能力在不同平台的语义必须保持一致，无法一致时在 API 文档中明确差异。

### 17.3 从裸机迁移到 RTOS

优先迁移顺序：时间/事件端口 → 通信和缓冲 → 设备任务 → 服务任务 → 应用编排。领域算法和状态机应尽可能保持不变；需要重写的部分通常是调度、同步、生命周期和错误恢复。迁移后重新评估栈、优先级、队列深度和最坏延迟。

## 18. 测试与架构审查

### 18.1 测试层次

- 纯算法、独立 Domain 和平台无关产品逻辑：主机单元测试和边界测试。
- 服务和协议：模拟时间、传输和错误，验证状态机与超时。
- 驱动：端口替身、仿真器或目标板测试。
- 系统：真实硬件冒烟、故障注入、长时间运行和资源观察。
- 发布：确认构建选项、版本、烧录文件、日志和回滚信息。

### 18.2 必测场景

#### 状态机

- 正常完整转移。
- 每个等待状态超时。
- 非法事件和非法状态。
- 取消、重试和恢复次数耗尽。
- tick 回绕附近的 deadline 判断。

#### 缓冲与通信

- 空、满、回绕、单字节和最大批量。
- DMA 数据跨多次回调组成一帧。
- 一次回调包含多帧。
- 错误长度、校验失败、半帧超时和噪声后重新同步。
- RX/TX 队列满及其诊断计数。

#### 并发

- ISR 在消费者读取边界时写入。
- 队列满、任务超时和锁竞争。
- 高优先级任务被低优先级资源阻塞。
- 任务栈高水位、看门狗和错误恢复同时发生。

#### 硬件

- 设备未连接、总线卡死、电源重启和通信中断。
- 传感器极值、执行器限幅和安全停机。
- 冷启动、重复初始化、软件复位和看门狗复位。

### 18.3 主机测试边界

独立 Domain、算法库、协议解析、环形缓冲和声明为平台无关的产品模块 SHOULD 在主机编译。时间、传输、存储和硬件端口用替身注入。测试替身必须可控制成功、忙、超时、错误和调用顺序，覆盖正常与失败路径。

### 18.4 硬件在环

HIL 至少记录固件版本、板卡版本、连接方式、输入刺激、预期输出、超时和日志。自动化价值最高的场景是烧录后冒烟、通信回环、传感器断连、看门狗和关键执行器安全状态。

### 18.5 架构审查清单

- [ ] 每个模块职责可用一句话描述。
- [ ] 依赖方向没有反向调用或未记录的跨层 include。
- [ ] HAL 和驱动私有类型没有泄露到应用、产品模块、服务或算法库。
- [ ] 独立 Domain 和平台无关模块没有依赖 BSP、RTOS 或 middleware 具体类型。
- [ ] 公共 API 说明生命周期、所有权、阻塞性和并发限制。
- [ ] ISR 只完成必要工作，复杂逻辑由任务或主循环处理。
- [ ] 所有等待都有事件、超时或硬件保证。
- [ ] 缓冲区、队列、栈和堆有上限与溢出策略。
- [ ] 错误可以传播、诊断、恢复或安全停机。
- [ ] 关键路径有最小可重复测试。
- [ ] 平台例外和生成代码边界已记录。
