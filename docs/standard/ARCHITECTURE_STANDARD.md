# 嵌入式软件架构与设计模式规范

> 版本：v1.0.0<br>
> 创建日期：2026-07-18<br>
> 发布日期：2026-07-24<br>
> 最后更新：2026-07-24<br>
> 状态：Active<br>
> 适用范围：个人 STM32、TI MSPM0、ESP32 及其他 MCU 的裸机/RTOS C 项目

本文档规定嵌入式软件如何分层、组织模块、隔离硬件、处理并发和演进。代码的命名、排版、注释和类型规则见
[CODING_STYLE.md](CODING_STYLE.md)。本文档以行业通用的依赖、所有权、接口、生命周期、并发、资源和验证原则为核心，并提供可映射到不同芯片、厂商 SDK 和 RTOS 的个人默认参考架构；具体平台 API 的使用方法由对应官方文档说明。

## 1. 使用方式与规则等级

### 1.1 规则等级

- **MUST**：默认必须遵守。
- **SHOULD**：通常应遵守；需要有明确理由才能偏离。
- **MAY**：可选实践，按项目规模决定。
- **EXCEPTION**：记录平台、性能或交付原因后允许的例外。

正文中的“必须、不得、禁止”与 MUST 等价，“通常应、推荐、优先”与 SHOULD 等价，“可以、可选”与 MAY 等价。带规则 ID 的加粗条款是稳定的核心规则，其后直到下一个规则 ID 或同级标题之前的正文、表格和细则用于具体化该规则。描述事实、解释原因和代码示例本身不构成独立规则；例外引用核心规则 ID，并补充具体小节和偏离内容。

严格约束的是依赖方向、数据所有权、并发边界、错误传播和硬件隔离；文件数量、抽象层数量和测试深度可以随项目规模裁剪。

### 1.2 版本和维护

本文档采用 SemVer：`MAJOR` 表示架构原则或章节体系不兼容变化，`MINOR` 表示新增模式或扩展，`PATCH` 表示文字、示例和链接修正。新增主题放入稳定章节，不因增加 RTOS、测试或新平台而重写目录；废弃内容先标记 `Deprecated`，并在变更记录中保留迁移说明。

### 1.3 规则 ID、符合性与例外

规范性规则使用 `ARCH-<CATEGORY>-NNN` 形式的稳定 ID。类别包括：

| 类别 | 主题 | 类别 | 主题 |
| --- | --- | --- | --- |
| `GOV` | 治理、适用性和架构产物 | `DEP` | 分区与依赖 |
| `API` | 接口、数据和所有权 | `LIFE` | 生命周期与启动 |
| `BSP` | 板级能力 | `DRV` | 驱动与平台适配 |
| `CONC` | 中断、事件和并发 | `SCHED` | 裸机调度 |
| `RTOS` | RTOS 任务与同步 | `COMM` | 通信与协议 |
| `ERR` | 错误、诊断和恢复 | `RES` | 内存、实时性和安全输出 |
| `SEC` | 安全边界 | `UPD` | 启动与升级 |
| `PWR` | 功耗和时钟状态 | `TEST` | 测试与符合性 |

**ARCH-GOV-001 [MUST] — 声明符合本规范的项目必须记录规范版本、工程规模、实际目录/分区映射、条件主题适用性、规则例外和验证证据。**

符合性按以下方式判定：

- MUST 全部满足，或存在仍在有效期内且已验证的例外。
- SHOULD 已采用，或记录未采用的技术原因、影响和替代措施。
- MAY 由项目自由选择，不影响符合性。
- 未记录的偏离视为不符合；项目可以表述为“带已登记例外符合”，不能省略例外后声明完全符合。

**ARCH-GOV-002 [MUST] — 例外必须引用真实规则 ID，并记录原因、影响范围、替代方案、验证方式、责任人和复审/失效日期。**

规则移动章节时保留 ID；废弃规则的 ID 不再复用。硬件额定值、法律法规、功能安全要求和平台不可违反的约束不能由本文档的例外流程豁免。安全关键项目还必须采用适用的行业安全标准、分析方法和审批流程。

### 1.4 参考边界

本文档参考 [ISO/IEC/IEEE 42010](https://www.iso.org/standard/74393.html) 的架构描述与符合性思想、[SEI 架构质量属性分析](https://www.sei.cmu.edu/library/early-analysis-of-software-architecture/)的方法，以及 [AUTOSAR Classic Platform](https://www.autosar.org/standards/classic-platform/) 等成熟嵌入式分层实践。本文档不声明符合这些标准，也不要求个人 MCU 项目引入 AUTOSAR、RTE、完整形式化模型或认证流程。

## 2. 目标与架构原则

行业通用的架构判断依据是系统需求、质量属性和约束，而不是目录名称或抽象层数量。嵌入式架构必须同时满足以下目标：

1. 业务逻辑不依赖具体芯片、引脚或厂商 HAL。
2. 在系统能力与接口语义不变时，硬件替换只影响 BSP、驱动或适配器，不迫使 Application 或 Domain 重写。
3. 中断、DMA、主循环和 RTOS 任务之间的责任清晰可审查。
4. 时间、内存、栈、队列和带宽等资源有可解释的上限。
5. 异常、超时和硬件故障有明确的传播和恢复路径。
6. 领域逻辑能够在主机环境中尽可能独立测试。
7. 架构能够从裸机逐步迁移到 RTOS，并将 RTOS API 限制在调度、同步和平台适配边界。

核心判断标准是：**上层依赖能力，不依赖实现；分区通过窄 API 协作，不通过共享内部数据协作。**

**ARCH-DEP-001 [MUST] — 每个跨分区依赖必须指向被依赖方的公共能力接口；下层不得通过 include、全局对象或回调主动取得上层实现。**

**ARCH-API-001 [MUST] — 每份可变数据和每项硬件资源必须有唯一权威所有者；其他分区只能读取快照、提交命令或通过明确的并发协议访问。**

**ARCH-RES-001 [MUST] — 资源使用和运行期工作量必须具有可说明的上限；有意的无限期阻塞只允许用于不承担完成期限的等待点，并必须定义唤醒、取消和关闭语义。**

**ARCH-GOV-003 [MUST] — 项目必须把关键质量属性写成可验证场景，至少覆盖适用的实时性、可靠性、可维护性、资源、可移植性和安全性要求。**

最小项目可以在 README 中用数行表格记录关键场景；标准和完整项目使用第 19.6 节模板。场景数量由风险决定，不为每个普通函数建立形式化场景。

## 3. 工程规模分级

**ARCH-GOV-004 [MUST] — 项目必须选择最小、标准或完整配置并满足对应最低要求；规模裁剪不能取消依赖、所有权、并发、错误和硬件安全边界。**

### 3.1 最小配置

适用于竞赛、实验和约 1～7 天的项目：

- 可以合并 `app`、`domain` 或 `services` 中的少量文件。
- 至少保留平台初始化、设备驱动、业务逻辑和配置的边界。
- 至少定义关键模块 API、主要状态机、通信格式和最终冒烟测试。
- 可以不用完整消息总线、依赖注入框架或主机单元测试。
- 不得因为时间紧而让业务代码直接写寄存器、直接修改其他模块的内部变量或无限等待硬件。

### 3.2 标准配置

适用于个人长期项目：

- 按第 4 章的职责分区组织目录和依赖。
- 驱动和服务支持多实例或明确的单实例封装。
- 对需要替换、主机测试或跨平台复用的时间、日志、通信和并发能力使用最小端口；固定实现使用直接公共 API。
- 对关键算法、通信解析和故障路径进行测试。
- 记录资源预算和平台适配差异。

### 3.3 完整配置

适用于复杂产品或多人协作：

- 维护正式的依赖图、接口契约、架构决策记录和变更审查。
- 引入持续集成、主机测试、硬件在环、故障注入和发布制品验证。
- 对实时性、内存、功耗、可靠性、安全和升级路径设定可测量指标。

### 3.4 条件主题适用性

**ARCH-GOV-005 [MUST] — 每个项目必须在架构说明中逐项判断以下主题是否适用；标记“不适用”时必须给出可复审的理由。**

| 条件主题 | 典型适用条件 | 最低输出 |
| --- | --- | --- |
| 外部通信与安全 | 接入不可信主机、网络、无线链路或可更新输入 | 信任边界、输入验证和失败策略 |
| Boot/固件升级 | 存在 Bootloader、现场升级、OTA 或双镜像 | 兼容性、完整性、掉电和回滚策略 |
| 持久化数据 | 使用 Flash、EEPROM、文件系统或 NVS | Schema 版本、完整性和迁移策略 |
| 低功耗与时钟切换 | 使用睡眠、动态时钟或外设电源域 | 功耗状态、唤醒源和恢复顺序 |
| 多核/cache/DMA | 存在多核、数据缓存或非一致 DMA | 内存所有权、cache 维护和屏障 |
| 危险执行器 | 输出可能造成人身、设备或机构损坏 | 安全状态、授权、限幅和独立停机路径 |
| 多板/多产品 | 同一代码支持多个板卡或产品配置 | 变体选择、能力差异和构建验证矩阵 |

最小项目可以把适用性结论放入 README；标准和完整项目将其纳入第 18.6 节的项目架构说明。条件在项目演进中发生变化时，必须重新评估相应结论。

## 4. 个人默认参考架构（Profile）与依赖模型

本章定义个人项目默认采用的参考架构。行业项目可以采用 AUTOSAR、分层架构、端口-适配器、组件架构或厂商框架规定的其他分区；只要记录实际映射并满足第 2 章的通用规则，就不要求目录名称完全一致。

**ARCH-DEP-002 [SHOULD] — 未受外部框架约束的个人 MCU 项目通常应采用本章 Profile；偏离时应记录替代分区、依赖方向和硬件隔离边界。**

本章以 Application、Domain、Services、Libraries、Middleware、BSP 和 Drivers 命名职责。采用其他架构或厂商框架时，项目必须先把实际分区映射到这些职责，再按本章 MUST 规则检查等价职责；规则约束职责和边界，不强制建立同名目录。Profile 的分区组合与目录命名是否采用，由 `ARCH-DEP-002` 判定。

默认 Profile 由产品能力、横向公共能力和硬件平台共同组成。箭头表示允许的编译期依赖，不表示所有调用必须经过固定的中间层。

```text
Application ──→ Domain / Services / Libraries / Middleware public API / BSP
Domain ───────→ Services / Libraries / Middleware public API / BSP 或项目端口
Services ─────→ Libraries / Middleware public API / BSP 或最小端口
BSP ──────────→ Drivers / Libraries / Vendor SDK/HAL / 生成代码
Drivers ──────→ Libraries / 最小硬件端口 / Vendor SDK/HAL / 寄存器
Middleware adapter ─→ BSP / Drivers / Vendor SDK/HAL
Drivers ─→ Vendor SDK/HAL ─→ Hardware
```

完成通知、回调、事件和数据可以在运行时向上流动，但不能改变编译期依赖方向。所有项目自有上层代码对硬件能力的访问必须经 BSP 或由 BSP 实现的项目端口；Drivers 和厂商类型不得向上泄露。目录用于表达职责和所有权，不要求每个分区都在所有项目中出现。

### 4.1 应用层（Application）

**ARCH-DEP-003 [MUST] — Application 只负责产品用例编排、运行模式和系统级策略，不拥有器件访问、通用算法或可下沉的领域规则。**

应用层负责产品入口、运行模式和用例编排，包括启动顺序、命令路由、任务注册、任务周期和优先级分配、模式切换与系统级降级策略。它负责“系统何时做什么”，不承载具体领域规则或器件访问细节。

应用层向主循环提供稳定的 `app_init()` 和 `app_run_once()` 入口。它可以调用 Domain、Services、Libraries、Middleware 公共 API 和 BSP 公共 API；不得直接访问寄存器、厂商 HAL 句柄、DMA 私有缓冲区或 Drivers 内部状态。

典型内容：`main` 之外的应用入口、任务注册表、模式管理、命令路由和系统状态编排。

### 4.2 领域层（Domain）

**ARCH-DEP-004 [MUST] — Domain 表达产品规则和策略，只依赖稳定能力接口，不依赖厂商类型、Driver 私有状态或 Application 流程。**

Domain 表达项目目标决定的系统能力、业务规则、状态机、领域模型和策略，是产品代码的核心。运动控制、感知判断、导航、通信协议语义、故障策略和单位明确的领域值类型都属于 Domain。`domain/` 可以按功能包拆分，每个功能包封装自身职责、状态和公共接口。

Domain 通过公共 API、事件或只读快照协作；它可以使用 Services、Libraries、Middleware 公共 API 和 BSP 的稳定语义 API。Domain 不得访问寄存器、厂商 HAL、生成代码内部对象或 Drivers 私有状态。需要在多板间复用或主机测试的 Domain 能力 SHOULD 通过项目端口隔离 BSP；板卡绑定清晰且规模较小的项目 MAY 直接依赖稳定的 BSP API。

PID、环形缓冲、CRC 等通用算法和数据结构归 Libraries；设备读取、引脚配置和板级资源绑定归 BSP 或 Drivers。

### 4.3 服务（Services）

**ARCH-DEP-005 [MUST] — Service 提供跨领域共享的系统能力，不包含具体产品流程，也不直接依赖项目 Driver 或厂商 HAL。**

Services 提供跨 Domain 功能共享、具有稳定 API 与明确生命周期或运行状态的系统能力，例如协作式任务调度、事件分发、时间、错误、日志、诊断、参数、持久化存储和看门狗管理。Services 不包含具体产品流程和领域决策。

Services 可以保持纯软件实现，也可以通过 BSP 公共 API 或显式注入的最小端口获得必要能力。例如任务调度器由 Application 注入单调时间源，存储服务通过 BSP 存储能力保存数据。Services 不得直接依赖项目自有 Drivers、寄存器或厂商 HAL 类型。

### 4.4 算法库与通用库（Libraries）

**ARCH-DEP-006 [MUST] — Library 必须保持无产品流程和无板卡绑定；需要外部能力时由调用者传入数据或由 Library 自己定义的最小接口。**

Libraries 提供无产品流程、无板卡绑定的可复用代码，例如 PID、滤波器、CRC、环形缓冲、数学运算、编码转换和容器。PID 算法本体属于 Library；定期采样、运行控制回路、处理模式和写入执行器输出属于 Domain 或 Application。

库依赖标准 C、同级基础库或经过声明的最小能力，不依赖 Application、Domain、Services、BSP 或具体 Drivers。需要内存、时间或同步能力时，由调用者显式传入，或将具有独立运行时性质的实现归入 Services 或 Middleware。

### 4.5 中间件（Middleware，可选）

**ARCH-DEP-007 [MUST] — Middleware 的第三方实现、项目配置和平台适配必须分开管理；产品规则不得进入 Middleware 适配代码。**

Middleware 表示具有独立生命周期和完整子系统性质的软件组件，例如 FreeRTOS、FatFs、LittleFS、LwIP、USB Device、LVGL 和第三方协议栈。

上层通过 middleware 公共 API 使用其能力。Middleware 与 BSP、Drivers 或厂商 HAL 的连接限于专用适配和配置边界；厂商或第三方 middleware 保持其原始目录和代码风格，项目配置、适配器和封装代码遵循本文档。

Middleware 公共 API 只在其语义属于调用方职责时直接使用。FreeRTOS 等内核 API 限制在 Application 调度、Services 并发实现和专用适配边界，不进入 Domain、Libraries 或声明为平台无关的 Services 公共接口。

未使用 middleware 的项目不创建空目录。单个算法文件、普通工具函数和简单设备驱动不归 middleware。

### 4.6 BSP（Board Support Package）

**ARCH-BSP-001 [MUST] — BSP 必须把板级资源、设备实例和硬件差异收敛为上层所需的稳定能力，不暴露厂商句柄、寄存器或 Driver 对象。**

BSP 负责把具体板卡的硬件资源组织为稳定的板级能力。接口按以下顺序设计：

```text
项目目标 → 系统能力要求 → BSP 语义契约 → Driver 选择与组合 → 厂商 SDK/HAL
```

BSP 只选择并组合实现系统能力所需的 Driver API；未被上层能力使用的 Driver 操作保持在底层。BSP API 表达电机输出、轮速反馈、姿态采集、状态指示和单调时间等板级能力，不暴露 GPIO、定时器通道、HAL 句柄或 Driver 对象。

#### 4.6.1 BSP 职责

BSP 同时承担以下职责：

- 资源绑定：引脚、电平、外设实例、DMA 通道、中断号、总线地址和设备实例。
- 语义统一：板级编号、单位、量程、坐标系、安装方向、有效电平和错误语义。
- 生命周期：初始化、启动、停止、复位、反初始化和重复调用规则。
- 资源所有权：保存 Driver 实例，路由 HAL/DMA/IRQ 事件，管理共享外设和缓冲区。
- 安全状态：规定上电、初始化失败、禁用、故障和复位期间的执行器输出。

Driver 实现器件或外设的原始能力；BSP 吸收当前板卡的连接、安装和资源差异；Domain 决定如何使用这些能力实现产品行为。BSP 不包含运动策略、路径规划、感知判断或任务周期等产品规则。

#### 4.6.2 Board 组合与能力分区

`bsp_board` 负责整块板的初始化顺序、能力可用性和安全状态，各能力文件负责其私有 Driver 配置和语义转换。例如：

```text
bsp_board
├── bsp_drive
├── bsp_wheel_feedback
├── bsp_imu
├── bsp_range_sensor
├── bsp_indicator
└── bsp_time
```

`bsp_board_init()` 在最小平台启动环境完成后、危险外设和输出授权前调用各能力的初始化接口，并在失败时进入确定的安全状态。Domain、Services 和 Application 的初始化由系统 Composition Root 负责，不放入 `bsp_board_init()`。BSP 可以持有静态 Driver 实例，但公共头文件只暴露 BSP 值类型、状态码和能力 API。

#### 4.6.3 生命周期与中断边界

**ARCH-BSP-002 [MUST] — BSP 必须规定每项板级能力的资源所有权、初始化/停止顺序、中断路由、失败状态和安全输出。**

执行器初始化按“确认复位安全状态 → 建立软件安全默认值 → 配置仍保持禁用的底层资源 → 初始化 Driver → 验证能力 → 按资源启用事件源 → 等待 Application 明确授权输出”的顺序进行。初始化完成不自动授予执行器输出权限；关键执行器必须提供幂等的禁用或安全状态接口。引脚复用或外设启用可能改变输出电平时，必须在改变前通过硬件默认值、GPIO 预装载或外部使能脚保证安全状态。

HAL、DMA 和 IRQ 回调位于平台/BSP 边界。回调只识别具体外设、保存必要状态并把事件路由给对应 Driver 或 BSP 能力；HAL 类型不继续传入 Domain。复杂解析、恢复和产品决策由任务上下文处理。

BSP 建立在 Drivers 和厂商 SDK/HAL 之上，向 Application、Domain 和 Services 提供稳定的板级语义 API。系统能力及其语义不变时，更换 MCU、引脚、外设实例或同类器件应主要修改 BSP、Drivers 和厂商配置；能力语义改变时，BSP 契约与其调用方必须一并更新。需要跨板复用或主机测试的上层能力可以在 BSP API 之外定义项目端口接口。

### 4.7 驱动（Drivers）与厂商 SDK/HAL

**ARCH-DRV-001 [MUST] — Driver 只实现外设/器件机制与原生能力，不包含板级身份、产品策略、调度周期、界面或系统恢复决策。**

Drivers 实现 MCU 外设或外部器件的机制与原生能力，包括初始化、读写、启动/停止、事务、DMA、中断接入、非阻塞状态和设备错误。驱动通过返回值、回调或底层事件报告结果，不包含产品模式、业务状态、任务周期、界面显示、遥测格式和系统恢复策略。

厂商 SDK/HAL 包括 STM32 HAL/LL、CMSIS、TI DriverLib、ESP-IDF/Arduino 底层 API、寄存器、启动文件和厂商生成代码。厂商类型限制在 Drivers、BSP 和专用平台适配边界。

#### 4.7.1 驱动分类与职责边界

驱动按被封装对象分为以下两类：

| 类型 | 典型对象 | 平台关系 | 公共能力 |
| --- | --- | --- | --- |
| MCU 外设驱动 | UART、SPI、I2C、ADC、PWM、定时器 | 通常与 MCU/SDK 绑定 | 外设传输、采样、计数和事件 |
| 外部设备驱动 | IMU、OLED、编码器芯片、电机驱动芯片 | 器件协议可独立，传输依赖可适配 | 器件寄存器、命令、样本和故障 |

外部设备驱动可以由平台无关的器件核心和平台相关的传输适配组成。能够稳定分离的寄存器协议、帧解析、校验、量程转换和设备状态机 SHOULD 位于器件核心；GPIO、总线、DMA、tick 和延时由最小端口或平台适配器提供。协议与厂商 SDK 紧密耦合、资源极小或没有复用价值的驱动 MAY 直接实现为平台专用驱动。

驱动边界遵守以下规则：

- 器件固有的地址、寄存器、命令、量程和故障属于 Driver。
- 板卡的引脚、外设实例、总线地址选择、安装方向、左右编号和有效电平属于 BSP。
- 器件原生单位转换可以属于 Driver；板级坐标、机械方向和产品单位语义由 BSP 统一。
- 外部器件固有的线协议解析属于 Driver；项目通信的帧格式、命令权限和业务语义按第 14 章拆分。
- 环形缓冲、CRC 和通用滤波归 Libraries；菜单、绘图、控制目标和调度标志不进入 Driver。
- Driver 可以报告设备故障和原始诊断，不决定降级、重启、报警显示或产品停机策略。
- Driver 不读取全局项目配置，不取得 Application、Domain 或系统组合根中的对象。
- 一个文件同时出现器件协议、板级资源和产品规则时，必须按所有权拆分或登记有期限的架构例外。

例如，DRV8874 Driver 可以提供输出、滑行、制动和故障读取；BSP 负责把两个实例绑定为左、右电机，处理 PWM 通道、方向极性和安全输出；Domain 负责速度闭环和运动策略。IMU Driver 可以输出器件坐标系下带单位的样本；BSP 应用安装方向和板级标定；Domain 判断姿态如何影响控制。

#### 4.7.2 驱动的组成形式

驱动按实际变化边界选择以下组成，不要求每个驱动都拆成相同文件数量：

```text
完整可移植设备驱动：

公共设备 API → 设备核心/状态机 → 最小传输端口 → 平台适配或 MCU 外设驱动

简单平台专用驱动：

公共驱动 API → 厂商 SDK/HAL 或寄存器
```

设备核心只依赖自身公共类型、私有状态和必要的最小端口。端口表达设备真正需要的操作，例如一次 SPI 事务、串口字节传输、GPIO 电平或单调时间；端口不复制整个 HAL API。平台适配器负责厂商状态码、句柄、回调和同步语义的转换。

推荐的组件内部布局如下，项目规模较小时可以保持在同一目录：

```text
drivers/<device>/
├── <device>.h               # 公共设备 API
├── <device>.c               # 设备核心或平台专用实现
├── <device>_port.h          # 可选的最小依赖端口
├── <device>_port_stm32.c    # 可选的平台适配器
└── <device>_private.h       # 可选的组件私有声明
```

端口仅由该设备使用时归设备组件所有；多个设备共享且需要仲裁的 UART、SPI 或 I2C 能力由 MCU 外设驱动、总线管理组件或 BSP 私有适配器提供。平台选择通过构建源文件或组合阶段完成，平台条件编译集中在适配边界。

#### 4.7.3 平台绑定与抽象选择

**ARCH-DRV-002 [SHOULD] — Driver 应采用满足已确认替换、复用或测试需求的最简单绑定方式；采用运行期函数表时，必须有明确的多实现或逐实例替换依据。**

驱动依赖采用能够满足已知变化需求的最简单绑定方式：

| 条件 | 绑定方式 | 说明 |
| --- | --- | --- |
| 单一平台、局部使用、无需主机替身 | 直接调用厂商 SDK/HAL | 平台类型保持在 Driver/BSP 边界 |
| 每个固件只选择一个平台实现 | 统一 API + 构建期/链接期选择实现 | 保留直接调用、内联和静态检查能力 |
| 同一固件需要为同一能力绑定不同类型的后端 | 句柄 + 端口函数表 | 在初始化时为各实例绑定实现 |
| 平台无关核心需要主机测试或独立发布 | 最小端口 + 测试替身 | 只抽象核心实际使用的能力 |

端口表示依赖契约，不等同于函数表。USART、SPI 和 I2C 可以使用函数表实现跨平台调用，但跨平台本身不自动要求运行期多态。固件在构建时已经确定 MCU，且同一接口只有一个实现时，使用相同公共 API 并在构建期选择 `stm32`、`mspm0` 或 `esp32` 源文件即可。多个同类外设实例只需要不同句柄或上下文。运行期需要为同一能力选择不同类型的后端，或者测试需要逐实例注入行为时，使用函数表；测试只替换整套实现时也可以在链接期选择测试替身。

函数表引入间接调用、上下文生命周期、空能力处理、一定的 ROM/RAM 成本，并削弱内联和部分静态分析能力。设计时 MUST 记录被替换的实现和绑定时机；无法指出第二个实现、测试替身或明确变化点时，不建立函数表。函数表位于依赖边界，设备的每个内部函数不建立一套对应函数指针。

项目不得建立一层与厂商 HAL 一对一同名转发的自有 HAL。公共接口必须收敛参数和语义，或者隔离已确认的平台差异；只改变函数名称不构成有效抽象。

#### 4.7.4 句柄、配置与资源所有权

**ARCH-DRV-003 [MUST] — Driver 实例、底层资源、异步缓冲区和回调上下文必须有唯一所有者及覆盖全部使用期的有效生命周期。**

多实例驱动默认使用“句柄 + 只读初始化配置 + 公共操作 API”。句柄拥有运行状态、缓冲索引、挂起事务和诊断计数；外部不得直接修改句柄字段。句柄存储按封装、静态分配和交付形式选择：

- 公共完整上下文适合源码交付且调用者必须静态分配的组件；字段仍只由 Driver 实现访问，并且默认不承诺布局/ABI 稳定。
- 不透明句柄适合需要强封装或稳定二进制接口的组件，由模块静态实例池、调用者工作区或受控创建接口提供存储。
- 裸机 Driver 默认不依赖堆分配；使用实例池时必须规定容量、耗尽错误和释放规则。

公共头文件只前向声明不完整句柄类型时，调用者不能直接定义该类型的对象；API 必须同时提供合法的存储和实例取得方式。公共接口不能要求调用者理解内部状态机。

初始化配置至少区分以下内容：

- 器件配置：地址、模式、量程、采样率和器件协议选项。
- 依赖绑定：总线/GPIO/时间端口及其上下文。
- 资源配置：调用者提供的缓冲区、容量和静态工作区。
- 通知配置：完成、数据可用和错误回调及其上下文。

Driver 必须说明配置是复制还是借用。借用的配置、端口上下文、缓冲区和回调上下文的生命周期必须覆盖全部使用期，不保存指向初始化函数栈变量的指针。异步发送必须说明数据是立即复制，还是在完成通知前持续借用；DMA 正在访问的内存不能被调用者修改或释放。

同一外设、DMA 通道、片选和硬件实例只能有一个明确所有者。共享总线由一个仲裁点串行化事务并规定优先级、超时和取消方式；不同设备驱动不得绕过仲裁点并发操作同一个厂商总线句柄。静态单实例仅用于客观唯一的资源，并保持内部状态私有。

#### 4.7.5 API 与行为契约

**ARCH-API-002 [MUST] — Driver 公共 API 必须定义生命周期前置条件、阻塞上限、所有权、执行上下文、并发限制、错误语义及失败后的确定状态。**

驱动公共 API 必须说明：

- 前置生命周期状态以及成功后的状态。
- 参数方向、长度、容量、单位、范围、坐标系和精度。
- 调用是否阻塞、最大等待时间、超时来源和可调用上下文。
- 返回值、允许的部分完成、`BUSY` 语义和重试条件。
- 缓冲区与对象所有权、有效期和并发访问限制。
- 回调的执行上下文、调用次数、顺序和重入限制。
- 失败后设备、输出参数和挂起事务处于何种确定状态。

公共状态码按驱动能力从参数错误、非法状态、忙、超时、传输错误、硬件错误、资源不足和不支持中选择，并保证所有实际失败路径可以区分。Driver 将厂商返回值映射为稳定状态码，并可通过只读诊断接口保留寄存器快照、厂商错误码和统计计数。调用者不得依赖未纳入契约的厂商错误值。

同步接口只用于具有明确且可接受最坏等待时间的操作。可能等待外设、总线、数据或机械动作的操作 SHOULD 使用 `start`/`submit`、事件、`process`/`poll` 和完成查询构成非阻塞协议。名称必须区分阻塞与异步行为，不能让普通 `read` 或 `write` 隐含无界等待。

#### 4.7.6 生命周期与状态机

非平凡驱动必须具有与实际生命周期一致的显式状态模型，并规定每个 API 在各状态下的行为。常见状态包括 `UNINITIALIZED`、`READY`、`BUSY`、`STOPPED` 和 `FAULT`，只选择能够表达真实行为的状态；简单 GPIO 驱动不需要构造形式化状态机。生命周期接口从第 6.5 节的接口族按需选择。

初始化遵守以下顺序：

1. 校验参数、依赖、缓冲区和当前状态。
2. 建立句柄、回调和安全默认输出。
3. 清除历史硬件状态和待处理中断。
4. 配置或验证底层资源。
5. 在全部软件状态有效后启用 DMA、中断或数据源。
6. 完成必要的器件探测，并进入确定状态。

`init` 不自动开始有风险的执行器输出。`stop` 终止新事务并进入契约规定的安全状态；`deinit` 在停止事件源和 DMA 后解除绑定。重复初始化、重复停止、取消和故障后复位的行为必须明确，安全停止 SHOULD 幂等。

#### 4.7.7 中断、DMA 与非阻塞处理

**ARCH-CONC-001 [MUST] — ISR 只执行硬件要求且有确定上限的工作；复杂解析、恢复、格式化、产品决策和普通公共回调必须延迟到任务上下文。**

平台 IRQ/HAL 回调负责识别外设并把最小事件路由到所属 Driver 实例。Driver 的 ISR 入口只完成硬件要求的确认、少量数据搬运、索引/计数更新和事件发布。确有低延迟需求的公共 ISR 回调必须以 `_isr` 明确命名，只能调用声明为 ISR-safe 的 API，并在接口契约中规定最坏执行时间；其他公共回调统一延迟到任务上下文。

发生次数有意义的事件使用计数器、队列或硬件位置差记录，不能只使用可能丢事件的布尔标志。ISR 与任务共享的数据必须满足目标 MCU 的原子性和内存可见性要求；`volatile` 只表达访问语义，不提供原子操作、互斥或完整的内存同步。

需要下半部处理的驱动提供有界的 `xxx_process()` 或 `xxx_poll()`。该接口每次调用的工作量、触发条件和最长允许间隔必须有契约；Driver 不决定系统任务周期和优先级，BSP/Application 在运行模型中安排调用。驱动状态机的每个等待状态必须有完成事件、有限超时或可以证明的硬件保证。

DMA 设计必须明确缓冲区所有权、cache 一致性、对齐、部分传输、完成顺序和错误后的缓冲状态。零拷贝只在生命周期和并发规则可以证明时使用；否则优先采用有界复制保持所有权清楚。

#### 4.7.8 错误、恢复与诊断边界

**ARCH-ERR-001 [MUST] — Driver 必须传播原始技术错误并保持可恢复或明确故障状态，不得决定产品级严重度、持续重试、降级或停机策略。**

Driver 负责检测并报告器件、传输、超时和非法状态错误，并使内部状态保持可恢复或明确进入 `FAULT`。Driver 可以执行协议所必需且次数有上限的局部恢复，例如清状态位、结束损坏事务或复位器件通信状态；是否持续重试、降级、重启模块或停止产品由 BSP、Domain 或 Application 按错误层级决定。

Driver 不直接操作 OLED、蜂鸣器、蓝牙、日志界面或系统模式。错误通知携带稳定错误码、来源和必要诊断上下文；接收边界可以补充系统时间并映射系统级严重度，由错误/诊断服务完成存储与呈现。持续故障必须限流或合并，不能在 ISR 或主循环中无限重复上报。

#### 4.7.9 第三方驱动与复用单元

第三方驱动保持上游目录、许可证、版本和代码风格，并记录来源与本地补丁。项目通过窄适配器处理其状态码、平台类型、回调和命名，不直接修改第三方源码以迎合项目风格；必须修改时维护可重复应用的补丁或清晰的 fork 版本。

可独立储备和复用的 Driver 单元至少包含公共头文件、实现、依赖说明、配置示例、支持的平台/器件版本、资源开销、执行上下文、测试状态和许可证。标记为平台无关的设备核心必须能在不包含厂商 SDK/HAL 头文件的构建中编译。

#### 4.7.10 驱动验证要求

驱动验证按边界分层：

- 设备核心：使用端口替身验证命令序列、解析、状态转移、超时和错误映射。
- 平台适配：在目标平台验证寄存器/HAL 配置、IRQ、DMA、时序和错误恢复。
- BSP 集成：验证资源绑定、单位/方向转换、初始化顺序和安全状态。
- 系统场景：验证并发负载、断连、总线故障、重复启停和长时间运行。

测试必须覆盖无设备、错误标识、短读写、缓冲区满、超时、重复回调、取消竞争和 tick 回绕等适用场景。没有经过目标板验证的实现必须在组件目录和发布说明中明确标记，不与已验证实现使用相同成熟度声明。

### 4.9 依赖与通信规则

- 所有跨目录调用使用公共头文件，不 include 其他模块的私有头文件或 `.c` 文件。
- 运行时向上通知使用返回值、回调、事件、队列或只读快照。
- 共享数据具有唯一所有者；外部通过 API 读取或提交命令。
- Services、Libraries 和 Middleware 是按需依赖，不要求无语义的逐层转发。
- 端口接口用于隔离确实存在的平台替换、测试或多实现需求，不为简单调用机械增加函数指针层。
- 性能、启动时序或厂商限制要求偏离依赖矩阵时，按照第 19.5 节记录例外、影响和验证结果。

## 5. 目录与文件组织

推荐的通用仓库结构：

```text
project/
├── app/                    # 产品流程和系统编排
├── domain/                 # 产品能力、领域模型、规则和策略
├── services/               # 时间、日志、错误、参数、协议等
├── libraries/              # PID、滤波、CRC、FIFO 等通用库
├── middleware/             # RTOS、文件系统、网络、GUI 等（按需）
├── bsp/                    # 板级资源和平台绑定
├── drivers/                # 外设/设备驱动
├── vendor/                 # 厂商 SDK、HAL、CMSIS 与生成支持文件
├── config/                 # 编译期和板级配置
├── tests/                  # 主机测试、替身和硬件测试说明
├── tools/                  # 生成、检查、烧录和分析脚本
├── docs/                   # 需求、硬件、架构和测试文档
├── .github/                # CI、Issue/PR 模板和自动化配置
├── CMakeLists.txt          # 或其他构建入口
├── README.md
└── LICENSE
```

小项目可以把上述目录合并为 `Core`、`Drivers`、`Users` 等少数目录，但必须在 README 或架构说明中写明实际映射。STM32CubeMX、TI SysConfig 等生成目录独立管理，用户代码放在可再生成的边界之外；ESP32 Arduino 项目也应把 Arduino API 访问集中在平台适配层。

### 5.1 STM32CubeMX 映射示例

```text
Core/Inc, Core/Src       → 生成的平台初始化和中断入口
Drivers/                 → CMSIS 与 STM32 HAL
User/App/                → 应用层
User/Domain/             → 产品能力、领域模型、规则和策略
User/Services/           → 共享系统服务
User/Libraries/          → 算法和通用库
Middlewares/             → 厂商或第三方中间件（按需）
User/Bsp/                → 板级资源绑定
User/Drivers/            → 手写设备驱动
```

`main.c` 保持薄：调用生成初始化、系统组合入口和调度入口；用户业务不散落在 CubeMX 的 `USER CODE` 块中。不得为了追求目录完全一致移动生成文件，破坏再次生成能力。

### 5.2 MSPM0 SysConfig 映射示例

```text
ti_msp_dl_config.*       → 生成代码
platform/                → DriverLib 小型封装
bsp/<board>/             → 引脚、外设实例和中断绑定
drivers/                 → 可复用设备驱动
app/, domain/, services/  → 项目手写功能与共享能力
libraries/               → 平台无关算法和通用库
middleware/              → RTOS、文件系统或协议栈（按需）
```

### 5.3 ESP32 Arduino 映射示例

Arduino `setup()` 只进行平台和系统初始化，`loop()` 只调用应用调度入口。`Serial`、`Wire`、`SPI` 和 GPIO 类型限制在 BSP、驱动或平台适配代码中；FreeRTOS 类型限制在 middleware、调度和同步边界。使用 ESP32 自带 RTOS 能力时仍遵守第 13 章的任务和同步规则。

### 5.4 文件职责

- `README.md`：用途、目标硬件、工具链、构建、烧录、基本验证和已知限制。
- `config/`：编译期选项、板卡选择、功能开关和资源上限；不放业务流程。
- `bsp/`：板卡引脚、外设句柄、时钟和 IRQ 绑定；不放通用算法。
- `drivers/`：设备能力和硬件时序；不直接决定产品模式。
- `app/`：产品流程、任务注册、运行模式和系统编排。
- `domain/`：项目能力、领域模型、规则、状态机和策略；可按功能建立子目录。
- `services/`：可被多个上层能力复用的系统服务；不反向调用具体业务。
- `libraries/`：平台无关算法和数据结构；不拥有产品流程和硬件资源。
- `middleware/`：具有独立生命周期的 RTOS、文件系统、网络、GUI 或第三方协议栈。
- `tests/`：测试输入、替身、断言和运行说明；不把临时调试代码混进生产模块。
- `docs/`：架构决策、硬件手册、接口契约和验证记录。
- `tools/`：可重复的生成、检查、打包和烧录辅助工具。

### 5.5 配置分层

**ARCH-API-003 [MUST] — 编译期配置、可调参数、运行命令、公开状态和内部状态必须按变化原因与所有权分开。**

配置和运行数据按变化原因与所有权分开：

- 平台配置：芯片、时钟、外设实例和 DMA。
- 板级配置：引脚、电平、传感器型号和执行器连接。
- 产品配置：功能开关、能力组合和资源上限。
- 可调参数：PID、阈值、默认速度、标定和用户设置。
- 运行命令：目标速度、目标角度、启动、停止和模式切换。
- 运行状态：当前速度、姿态、故障、任务状态和统计。
- 内部状态：Driver 句柄、PID 积分、DMA 索引和状态机私有数据。

平台、板级和产品配置通常在构建或初始化阶段确定；可调参数可以在运行期验证后更新和持久化；运行命令通过具名动作 API 提交；运行状态通过只读快照或查询 API 发布；内部状态不对外开放。驱动公共头文件不保存“某个项目恰好使用”的速度和引脚值，这些值由 BSP 或配置对象注入。

### 5.6 构建边界

**ARCH-DEP-008 [MUST] — 构建系统必须能识别各职责分区的源文件和公开依赖，并阻止平台类型进入声明为平台无关的目标。**

每个职责分区应成为清晰的构建目标或至少具有独立源文件列表和 include 可见性规则。独立 Domain、纯算法库和声明为平台无关的服务应能在不链接厂商 SDK/HAL 的情况下编译。平台选择通过构建系统选择 BSP、驱动或适配器源文件，不在每个组件内部散布平台条件编译。CI 至少通过独立编译目标、禁止头文件扫描或依赖图检查中的一种方式验证边界。

## 6. 模块设计与 API 契约

### 6.1 模块边界

**ARCH-API-004 [MUST] — 模块必须具有单一可命名职责、明确所有者和最小公共接口；独立生命周期、错误路径或替换需求构成拆分依据。**

模块应具有单一、可命名的职责，拥有自己的状态和资源，并通过头文件暴露最小能力集合。判断一个模块是否应拆分时，检查：它是否有独立生命周期、独立测试方式、独立错误路径或独立平台替换需求。

### 6.2 接口形式

接口形式由模块类型、生命周期和实例数量决定：

```c
/* 多实例硬件驱动：句柄 + 配置 + 状态码 */
/* motor_handle_t 的存储方式由驱动接口契约规定。 */

motor_status_t motor_init(motor_handle_t *motor, const motor_config_t *config);
motor_status_t motor_set_output(motor_handle_t *motor, int16_t output_permille);

/* 纯算法：不需要句柄时使用输入/输出参数 */
int32_t pid_compute(
    const pid_config_t *config,
    pid_state_t *state,
    int32_t target,
    int32_t actual);

/* 系统唯一服务：隐藏内部实例，通过能力 API 访问 */
system_status_t system_time_ms(uint32_t *time_ms);
```

公共接口必须说明生命周期、所有权、阻塞性、超时、错误码、ISR/任务限制和线程安全。配置结构体用于初始化和板级绑定；运行时参数通过动作接口或明确的参数接口修改。

### 6.3 句柄、单实例和多实例

默认设计为多实例：句柄由调用者静态分配、由模块静态实例池提供，或放入调用者提供的固定工作区；具体方式必须与句柄类型的可见性一致。模块不依赖隐藏的全局项目状态。以下情况可以单实例：系统时钟、唯一看门狗、板载唯一 LED 等客观唯一资源。单实例也必须隐藏状态并提供 API，不能暴露可写全局对象。

### 6.4 依赖注入与适配器

需要时间、日志、GPIO、传输、存储、锁或队列的模块，按第 4.7.3 节的绑定规则选择直接 API、配置结构体、链接期适配或运行期函数表。这样可以：

- 让需要复用和主机测试的产品逻辑脱离芯片和 RTOS。
- 在主机测试中提供替身。
- 在 STM32、MSPM0、ESP32 之间替换实现。
- 在裸机和 RTOS 之间替换调度/同步实现。

只有在增加的抽象能够被替换、测试或复用时才引入；单个简单 GPIO 包装不应为了形式而建立多层接口。

### 6.5 标准驱动接口族

驱动按实际需要从下列接口族中选择，不要求实现所有函数：

```c
driver_status_t xxx_init(xxx_handle_t *handle, const xxx_config_t *config);
driver_status_t xxx_deinit(xxx_handle_t *handle);
driver_status_t xxx_start(xxx_handle_t *handle);
driver_status_t xxx_stop(xxx_handle_t *handle);
driver_status_t xxx_reset(xxx_handle_t *handle);
driver_status_t xxx_read(xxx_handle_t *handle, xxx_sample_t *sample);
driver_status_t xxx_write(xxx_handle_t *handle, const xxx_command_t *command);
driver_status_t xxx_process(xxx_handle_t *handle);
void xxx_on_event_isr(xxx_handle_t *handle, xxx_irq_event_t event);
```

`init` 只建立可验证的初始状态；`start` 开始运行；`stop` 将输出置于安全状态；`deinit` 释放或解绑资源。简单驱动可以合并部分阶段，但契约仍需明确。

### 6.6 运行参数接口

**ARCH-API-005 [MUST] — 参数必须由实际使用该值的组件拥有，并通过类型化、可校验、支持多实例的接口读取和整体应用。**

参数具有唯一权威所有者。Domain、Service 或 BSP 组件保存实际运行值，负责最终校验、原子生效和副作用；外部不能取得内部可写变量、算法对象或 Driver 句柄。普通配置使用 copy-out 与整体 apply 接口：

```c
component_status_t component_get_config(
    const component_t *component,
    component_config_t *config);
component_status_t component_apply_config(
    component_t *component,
    const component_config_t *config);
```

同一事务需要更新的参数放入一个配置对象统一提交。`apply` 必须在修改运行状态前完成类型、范围、数值有效性、当前生命周期和跨字段约束校验。硬件应用可能部分失败时，接口必须选择并记录以下结果之一：恢复旧配置、保持安全的部分配置并返回详细状态，或进入明确 `FAULT`；不能返回失败后留下无法查询的混合状态。接口还要说明更新后保留还是重置历史状态。不同类型、带复杂副作用或需要原子更新的一组参数，不使用无类型的 `void *`、万能整数接口或内部字段指针。客观单实例组件可以省略实例参数，但必须在模块说明中登记单实例理由。

#### 6.6.1 参数服务

**ARCH-API-006 [SHOULD] — 参数数量、访问入口或持久化需求达到统一管理价值时，应由 Parameter Service 管理元数据和访问，不转移参数所有权。**

参数数量较多、需要统一调参、权限控制或持久化时，可以建立 Parameter Service。Parameter Service 管理参数访问规则，不成为组件实际参数的所有者。每个参数描述至少包含：

- 稳定 ID 和可读名称。
- 值类型、单位、范围和调节步长。
- 只读/读写权限与允许的执行上下文。
- 是否持久化、是否允许运行中修改、是否需要系统停止或重启。
- 读取和写入绑定函数。

Parameter Service 通过绑定函数调用所有者的公共配置 API，不保存指向组件内部字段的裸指针。服务层范围检查用于协议、UI 和通用访问控制，组件所有者仍执行最终校验。

```c
parameter_status_t parameter_get(
    parameter_id_t id,
    parameter_value_t *value);

parameter_status_t parameter_set(
    parameter_id_t id,
    const parameter_value_t *value);

parameter_status_t parameter_adjust(
    parameter_id_t id,
    int32_t step_count);
```

参数绑定表默认静态定义，并由 Application 在组合阶段统一注册。Domain、Services 和 BSP 不因可调参数而依赖具体通信协议、显示界面或持久化后端。最小项目可以直接使用各组件的类型化配置 API，不创建通用 Parameter Service。

#### 6.6.2 参数、命令与状态边界

可调配置进入 Parameter Service；启动、停止、移动和目标角度等运行命令进入 Application 或 Domain 的具名命令 API；当前速度、姿态和故障等运行状态通过只读快照或 Telemetry 发布；Driver 句柄、PID 积分和 DMA 索引保持私有。值类型和配置副本可以跨分区传递，内部可写对象不能跨越所有权边界。

板级静态配置由 BSP 私有管理，不注册为运行参数。需要现场保存的 IMU 零偏、电机死区和传感器校准可以由 Parameter Service 统一访问，但必须通过对应 BSP 校准 API 应用。

#### 6.6.3 持久化与生效流程

启动时按“编译期默认值 → 加载版本化记录 → 校验版本/长度/完整性 → 迁移 → 组件 apply”的顺序建立运行参数。运行期修改先通过组件校验并生效，再标记持久化数据为 dirty；后台任务延迟合并写入或由显式保存命令提交，不因每次调节立即擦写 Flash。Parameter/Storage Service 必须能够查询 dirty、保存中、已保存和保存失败状态；运行值与最后成功持久化值不一致时，UI、协议和关机流程不能把它误报为已保存。

持久化记录必须包含版本和完整性校验，并定义掉电一致性、写入失败、旧版本迁移和恢复默认值策略。Settings/Storage Service 负责存储流程；参数所有者负责运行值和领域约束；Application 决定保存、恢复和故障后的产品策略。

### 6.7 数据共享方式

| 方式 | 适用场景 | 关键约束 |
| --- | --- | --- |
| 直接函数调用 | 同步、一对一、调用链明确 | 不形成反向依赖 |
| Getter/快照 | 一个生产者、多个只读消费者 | 说明一致性和时间戳 |
| 命令接口 | 消费者要求生产者执行动作 | 不暴露内部字段 |
| 回调 | 一个明确消费者的异步完成 | 说明执行上下文和时限 |
| 队列 | 跨任务、有缓冲需求 | 容量和满队列策略明确 |
| 发布订阅 | 多消费者、动态组合 | 生命周期和丢失策略明确 |

返回内部可写指针通常违反所有权。需要高效读取大型数据时，可以返回 `const` 视图或双缓冲快照，但必须说明有效期和并发规则。

### 6.8 系统组合根

**ARCH-LIFE-001 [MUST] — 每个固件可执行目标必须有一个系统 Composition Root，集中决定实例创建、依赖绑定和跨分区初始化顺序。**

系统 Composition Root 通常位于 `app_composition.c` 或 `system_composition.c`。`bsp_board.c` 是 BSP 内部装配边界：它创建 Driver 实例、绑定平台资源并组成板级能力，再由系统 Composition Root 调用。系统 Composition Root 创建 Services、Domain 和 Application 实例，并为它们绑定 BSP 能力或项目端口。

小项目可以将系统 Composition Root 与 BSP 内部装配放入同一个 `system.c`，但仍保留 BSP 公共 API 与上层模块 API；合并文件不向上暴露 Driver 句柄。Driver、Domain 和 Services 不 include 组合根头文件，也不从组合根主动查询依赖。

```c
/* bsp_drive.c */
static motor_handle_t left_motor;

static const motor_config_t left_motor_config = {
    .pwm_channel = BOARD_MOTOR_LEFT_PWM,
    .direction_pin = BOARD_MOTOR_LEFT_DIRECTION,
};

/**
 * @brief  初始化板级驱动能力
 * @retval 成功返回 BSP_STATUS_OK，否则返回对应错误状态
 */
bsp_status_t bsp_drive_init(void)
{
    motor_status_t motor_status;

    motor_status = motor_init(&left_motor, &left_motor_config);
    if (motor_status != MOTOR_STATUS_OK) {
        return bsp_status_from_motor(motor_status);
    }

    return BSP_STATUS_OK;
}
```

系统 Composition Root 负责调用 `bsp_board_init()` 并把 BSP 能力或端口传入上层对象；BSP 内部装配只把 Driver 句柄或硬件端口传入 BSP 私有实现。BSP 公共 API 对上提供能力，不返回 Driver 句柄。个人小项目可以对上层对象使用受控 getter，但 getter 只能位于明确的资源访问边界，只返回只读视图或具有受限操作能力的接口。普通模块不得使用 getter 任意取得无关对象。

### 6.9 模块独立性检查

- 模块 `.c` 第一个 include 是自身头文件。
- 不 include `main.h`、项目总头文件或应用层头文件。
- 不硬编码板级引脚和外设实例。
- 状态由句柄或内部 `static` 对象拥有。
- 所有外部访问经过公共 API。
- 模块可在最小测试构建中独立编译。
- 多实例需求明确；单实例有客观理由。
- 平台专用内容位于端口或适配器实现。

## 7. 生命周期与初始化

**ARCH-LIFE-002 [MUST] — 初始化和关闭顺序必须来自实际依赖图；每个事件源只在句柄、缓冲区、回调和失败路径就绪后启用。**

每个对象只在其直接依赖就绪后初始化，相互无依赖的对象没有固定先后关系。典型 MCU 项目可按以下阶段组织：

```text
复位安全状态与最小启动环境
  → 不激活危险输出的平台时钟、内存和基础外设
    → BSP/Driver 句柄、缓冲区、回调和安全默认值
      → 清 pending 并按资源启用 DMA/IRQ/数据源
        → 平台无关 Services 与 Domain
          → Application 任务注册
            → 明确授权执行器并进入运行模式
```

每个初始化 API 必须说明：依赖的前置条件、是否可重复调用、失败后的对象状态、是否需要反初始化以及启动后由谁调度。平台初始化、驱动初始化和业务启动分开；不要在驱动初始化中隐式开启尚未配置的应用行为。

### 7.1 初始化失败与降级

初始化链遇到失败时，停止启动依赖该能力的模块，并选择安全停机、有限重试、降级运行或诊断模式。不能忽略错误继续启动，再由空句柄或无效硬件状态触发更难定位的故障。

每个可选模块在产品配置中明确是否允许缺失。例如显示模块失败可以降级为串口诊断；电机反馈失败通常必须禁止运动。降级策略属于应用层，不应写死在驱动中。

### 7.2 幂等与重复初始化

每个模块明确重复调用 `init`、`start`、`stop` 和 `deinit` 的行为。推荐 `stop` 和安全动作幂等；重复 `init` 可以返回 `ALREADY_INITIALIZED`，也可以在完全停止后重建，但不能隐式泄漏资源或重复注册中断。

### 7.3 中断启用与关闭顺序

句柄、缓冲区、回调和状态机全部就绪后再启用中断。初始化期间产生的待处理中断必须在启用前清除。关闭顺序相反：先禁止新事件，再停止 DMA/外设，最后释放或清空状态。

```c
/**
 * @brief  启动 UART 异步接收
 * @param  uart    已初始化的 UART 实例
 * @retval 成功返回 DRIVER_STATUS_OK，否则返回对应错误状态
 */
driver_status_t uart_start(uart_handle_t *uart)
{
    platform_irq_disable(uart->irq);
    platform_irq_clear_pending(uart->irq);
    uart_reset_fifo(uart);
    uart_start_rx_dma(uart);
    platform_irq_enable(uart->irq);
    return DRIVER_STATUS_OK;
}
```

## 8. 状态机模式

**ARCH-API-007 [MUST] — 存在运行期等待、重试、超时、分阶段操作或故障恢复的模块必须使用有界非阻塞状态机或具有等价可证明行为的实现。**

初始化阶段经过实时预算允许的短阻塞操作可以记录为例外；运行阶段不得用无界轮询代替状态机。

状态机至少定义：

- 状态集合和初始状态。
- 外部事件和内部条件。
- 状态转移。
- 每个状态的进入动作、执行动作和退出动作。
- 超时、非法事件和错误恢复。
- 完成、失败和取消的通知方式。

```c
typedef enum {
    SENSOR_STATE_IDLE,          /* 空闲，允许接收新的采样请求 */
    SENSOR_STATE_STARTING,      /* 已接受请求，等待启动硬件 */
    SENSOR_STATE_WAITING,       /* 转换已启动，等待完成事件 */
    SENSOR_STATE_READY,         /* 样本可由读取接口取走 */
    SENSOR_STATE_RECOVERY_WAIT, /* 局部恢复退避期间 */
    SENSOR_STATE_FAILED,        /* 恢复次数耗尽，等待上层策略 */
} sensor_state_t;

/**
 * @brief  推进一次传感器状态机
 * @param  sensor    已初始化的传感器实例
 * @retval 状态机推进成功返回 SENSOR_STATUS_OK，否则返回对应错误状态
 */
sensor_status_t sensor_process(sensor_handle_t *sensor)
{
    sensor_status_t status;

    switch (sensor->state) {
        case SENSOR_STATE_IDLE:
            break;
        case SENSOR_STATE_STARTING:
            status = sensor_start_conversion(sensor);
            if (status != SENSOR_STATUS_OK) {
                return sensor_schedule_recovery(sensor, status);
            }
            sensor->deadline_ms = time_deadline_after_ms(SENSOR_CONVERSION_TIMEOUT_MS);
            sensor->state = SENSOR_STATE_WAITING;
            break;
        case SENSOR_STATE_WAITING:
            if (sensor_conversion_done(sensor)) {
                status = sensor_read_result(sensor);
                if (status != SENSOR_STATUS_OK) {
                    return sensor_schedule_recovery(sensor, status);
                }
                sensor->state = SENSOR_STATE_READY;
            } else if (time_deadline_reached(sensor->deadline_ms)) {
                return sensor_schedule_recovery(sensor, SENSOR_STATUS_TIMEOUT);
            }
            break;
        case SENSOR_STATE_READY:
            break;
        case SENSOR_STATE_RECOVERY_WAIT:
            if (!time_deadline_reached(sensor->retry_deadline_ms)) {
                break;
            }
            status = sensor_recover(sensor);
            if (status != SENSOR_STATUS_OK) {
                return sensor_schedule_recovery(sensor, status);
            }
            sensor->recovery_count = 0U;
            sensor->state = SENSOR_STATE_IDLE;
            break;
        case SENSOR_STATE_FAILED:
            break;
        default:
            sensor->state = SENSOR_STATE_FAILED;
            return SENSOR_STATUS_INVALID_STATE;
    }

    return SENSOR_STATUS_OK;
}
```

`sensor_start()` 只在 `IDLE` 接受请求并转入 `STARTING`；读取接口只在 `READY` 复制样本并转回 `IDLE`。`sensor_schedule_recovery()` 增加恢复计数，未耗尽时设置有限退避 deadline 并进入 `RECOVERY_WAIT`，耗尽后进入 `FAILED`。状态机每次调用只完成有限工作，不在状态内部等待；完成、超时、非法状态和恢复耗尽均有确定结果。

## 9. 事件驱动与消息传递

### 9.1 事件模型

**ARCH-CONC-002 [MUST] — 异步事件必须定义类型所有者、载荷所有权、时间语义、投递上下文、容量和丢失/溢出策略。**

事件描述已经发生的领域或设备事实，包含来源、类型、可选数据，以及需要判断顺序或新鲜度时的时间戳。寄存器状态由 Driver/BSP 转换成稳定事件，生产者不直接调用消费者的内部函数。

裸机可以使用事件位、固定数组或环形队列；RTOS 可以映射到队列、事件组或任务通知。上层只依赖项目事件接口，不依赖具体 RTOS 类型。

### 9.2 发布-订阅和消息总线

**ARCH-CONC-003 [SHOULD] — 一对一且调用关系明确的通信应使用直接 API；只有多消费者、生命周期解耦或异步缓冲需求成立时才引入发布-订阅。**

发布-订阅适合一个事件有多个消费者、生产者和消费者生命周期不同或需要替换消费者的场景。使用时必须规定：

- topic/事件 ID 的所有权。
- 消息大小、队列深度和溢出策略。
- 消息是复制、引用还是借用。
- 消费顺序、优先级和丢失容忍度。
- 订阅者注销和生命周期。

简单的一对一调用优先使用函数或直接接口，不为单个生产者/消费者引入全局消息总线。

### 9.3 生产者-消费者与 FIFO

UART DMA、传感器采集和协议解析通常采用：

```text
硬件 → DMA/ISR → FIFO → 解析任务 → 领域事件 → 应用
```

FIFO 规定单写者/单读者优先；读写索引、满/空条件、溢出策略和临界区必须明确。DMA 缓冲区的所有权在回调完成前不转移；消费者不得直接修改生产者仍在使用的缓冲区。

### 9.4 事件结构和队列接口

```c
typedef enum {
    EVENT_SENSOR_SAMPLE_READY, /* 新传感器样本已发布 */
    EVENT_MOTOR_FAULT,         /* 电机进入故障状态 */
    EVENT_COMMAND_RECEIVED,    /* 收到一条完整命令 */
} event_type_t;

typedef struct {
    event_type_t type;
    uint32_t timestamp_ms;
    uint16_t source;
    event_payload_t payload;
} event_t;

event_status_t event_publish(const event_t *event);
event_status_t event_try_receive(event_t *event);
```

事件载荷默认小且定长。大型数据通过对象池句柄、只读快照或引用计数对象传递，并明确释放责任。禁止把栈对象指针或会被 DMA 继续覆盖的缓冲区投递到异步队列。

### 9.5 队列满和事件合并

队列满必须选择显式策略：

- 控制命令和故障：保留高优先级事件，必要时触发安全状态。
- 连续传感器值：可以只保留最新样本并累计丢弃计数。
- 协议字节流：不得静默丢弃，应复位帧解析并上报溢出。
- 日志：允许按等级丢弃，但要记录丢弃数量。

周期性“刷新”事件可以用事件位合并，不能让相同事件无限堆积。队列深度根据峰值生产速率、最大消费延迟和可容忍突发量计算。

### 9.6 回调规则

回调适合一个明确消费者的完成或错误通知。注册时必须说明回调上下文、生命周期、调用次数、注销行为和是否可重入。普通回调只在任务上下文执行；显式 `_isr` 回调才允许在 ISR 执行，并遵守第 4.7.7 节的限制。模块不得在持锁或临界区中调用未知回调。注销必须定义与正在执行回调的竞争结果；对象停止或销毁后不得再调用其回调。

## 10. 端口-适配器

**ARCH-API-008 [MUST] — 引入端口时，端口必须由需要该能力的上层组件定义，并只包含调用方实际需要且可以稳定约定的语义。**

端口描述上层所需的能力，适配器实现平台细节。典型端口包括：

- 时间和延时。
- GPIO、PWM、ADC、传感器。
- 串口、SPI、I2C 和网络。
- 日志和诊断。
- 非易失存储。
- 临界区、锁、队列和事件。

```c
typedef struct {
    uint32_t (*now_ms)(void *context);
    void (*sleep_until)(void *context, uint32_t deadline_ms);
    void *context;
} time_port_t;
```

裸机适配器可以读取系统 tick 并返回主循环；RTOS 适配器可以映射到系统时钟和任务延时。端口接口不能泄露 `HAL_HandleTypeDef`、FreeRTOS `QueueHandle_t` 或 Arduino 对象。

### 10.1 时间模型

**ARCH-CONC-004 [MUST] — 调度、超时和样本新鲜度必须使用单调时间；日历时间、RTC 和联网校时不得直接作为 deadline 时间源。**

每个时间端口必须规定 tick 单位、分辨率、位宽、回绕周期和是否可在 ISR 调用。模运算 deadline 比较只在持续时间小于计数器半范围时成立；接口必须限制最大超时或使用更宽的扩展计数器。周期调度使用绝对 release/deadline，延时使用 duration，二者不能只靠无单位整数隐式区分。

休眠或时钟切换可能暂停 tick 时，Power/BSP 适配器必须说明单调时间是否连续、如何补偿以及哪些 deadline 在唤醒后过期。`WAIT_FOREVER` 只能使用明确的具名常量，并且不得出现在 ISR、硬实时路径、本规范要求有界的操作或承担完成 deadline 的调用链中。允许无限期等待时，还必须满足 `ARCH-RES-001` 的唤醒、取消和关闭要求。

## 11. 组件化与接口表

多实例状态使用句柄表达；同一能力需要在运行期绑定不同类型的实现，或测试需要逐实例注入行为时，使用函数指针表：

```c
typedef struct {
    transport_status_t (*read)(
        void *context,
        uint8_t *data,
        size_t capacity,
        size_t *read_length);
    transport_status_t (*write)(
        void *context,
        const uint8_t *data,
        size_t length,
        size_t *written_length);
    void *context;
} transport_port_t;
```

规则：

- 函数指针表在初始化后默认为只读。
- `context` 的生命周期必须长于所有调用。
- 初始化时拒绝缺失的必需函数；可选能力由安全包装接口返回 `UNSUPPORTED`，不调用空指针。
- 接口表用于可替换能力，不用于隐藏普通函数调用。
- 读写接口必须说明全有或全无、部分完成、`BUSY`、超时及输出长度在失败时的值。
- 回调执行上下文、阻塞性、重入性和线程安全必须写入接口契约。

### 11.1 模式选型表

设计模式用于解决已经存在的变化、并发或复用问题，不作为“专业程度”的装饰。选择前先回答：什么会变化、谁拥有状态、调用是同步还是异步、资源成本是否可接受。

| 问题 | 首选模式 | 不必使用的情况 |
| --- | --- | --- |
| 分阶段、等待和超时 | 状态机 | 一次同步计算即可完成 |
| 替换硬件或平台实现 | 端口-适配器/策略 | 永远不会替换的局部函数 |
| 一个事件通知多个模块 | 发布-订阅/观察者 | 明确的一对一调用 |
| 跨任务传递动作 | 命令 + 有界队列 | 同一调用栈内立即执行 |
| 异步设备独占资源 | Active Object/设备任务 | 裸机单调用者简单设备 |
| 创建固定类型实例 | 工厂/组合根 | 只有一个静态实例 |
| 持久化与领域隔离 | Repository/存储端口 | 单个驱动寄存器读写 |
| 可替换算法 | 策略模式 | 只有一个稳定算法 |

### 11.2 策略模式

策略模式适合控制算法、滤波器、路径选择或校验方法需要替换的场景。C 中使用函数指针表和上下文：

```c
typedef struct {
    int32_t (*compute)(void *context, int32_t target, int32_t actual);
    void (*reset)(void *context);
    void *context;
} controller_strategy_t;

typedef struct {
    controller_strategy_t controller;
    motor_port_t motor;
} motion_control_t;
```

规则：

- 在初始化时绑定策略，运行期不随意改写函数表。
- 策略输入输出使用领域类型，不泄露驱动句柄。
- 不同策略保持相同单位、范围和失败语义。
- 只有一个简单算法且没有测试替换需求时，直接函数调用更清楚。

### 11.3 命令模式

命令对象适合把“请求执行动作”从产生者传递给拥有资源的任务。

```c
typedef enum {
    MOTOR_COMMAND_SET_SPEED,   /* 设置目标速度 */
    MOTOR_COMMAND_STOP,        /* 停止电机输出 */
    MOTOR_COMMAND_CLEAR_FAULT, /* 清除已确认的故障状态 */
} motor_command_type_t;

typedef struct {
    motor_command_type_t type;
    union {
        int16_t speed;
    } parameter;
} motor_command_t;
```

命令队列必须规定：同类命令是否覆盖、停止命令是否具有优先权、队列满时如何保证安全动作、命令过期后是否仍执行。紧急停止不应因为普通命令队列已满而丢失，可以使用专用高优先级事件或硬件安全路径。

### 11.4 Active Object / 设备拥有者

RTOS 中可以让一个任务独占 I2C、SPI、文件系统或复杂设备，其他任务通过命令队列请求服务。设备拥有者串行执行事务，因此调用方无需直接锁底层句柄。

```text
传感器任务 ─┐
显示任务 ───┼→ I2C 请求队列 → I2C Owner Task → HAL/DMA
参数任务 ───┘                       ↓
                         完成事件/响应队列
```

适用条件：事务可能阻塞、调用者较多、总线需要统一超时恢复。代价是队列、任务栈、调度延迟和异步接口复杂度。裸机或只有一个调用者时，普通总线服务加状态机通常足够。

### 11.5 Repository / 持久化端口

Domain 不直接读写 Flash 地址、NVS key 或文件路径，通过语义接口保存配置：

```c
typedef struct {
    settings_status_t (*load)(void *context, system_settings_t *settings);
    settings_status_t (*save)(void *context, const system_settings_t *settings);
    void *context;
} settings_repository_t;
```

存储适配器负责版本、校验、磨损、掉电一致性和平台 API。Domain 只感知完整设置对象是否加载或保存成功。对于只有一个校准值的小项目，可以使用简单存储服务，不需要建立通用数据库式 Repository。

### 11.6 双缓冲与快照

高速生产者、低速消费者共享一组数据时，可以使用双缓冲：生产者写非活动缓冲，完成后原子交换活动索引；消费者获得只读快照。规则：

- 交换前生产者必须完成整帧写入。
- 消费者使用期间缓冲不能被重新作为写缓冲，或必须允许覆盖旧快照。
- 数据包含序列号和时间戳，用于识别跳帧和过期。
- 多消费者需要引用计数、三缓冲或复制，不能假设所有消费者同时完成。

### 11.7 状态模式与分层状态机

状态数量较少时，一个 `switch` 最容易审查。状态超过约十个、存在明确父状态或多个正交区域时，可以拆分状态处理函数或使用层次状态机。不要仅为了消除 `switch` 使用大量函数指针，使转移关系难以搜索。

分层状态机需要明确：父状态处理哪些公共事件、未处理事件是否向父级传播、进入/退出顺序，以及历史状态是否保留。生成状态机代码时，模型文件和生成器版本必须进入仓库。

### 11.8 观察者与发布-订阅区别

观察者通常同步调用已注册回调，适合少量、确定执行时间的订阅者；发布-订阅通常经过事件队列或 broker，适合异步和多任务。同步观察者必须防止：

- 订阅者在回调中注销自己导致遍历失效。
- 某个回调阻塞整个发布者。
- 回调反向调用发布者形成递归。
- ISR 发布时调用不具备 ISR 安全性的订阅者。

### 11.9 工厂与组合根

C 项目通常不需要通用反射式工厂。实例数量和类型在编译期已知时，由组合根静态创建最清楚。只有产品配置需要选择多个实现之一时，才使用小型工厂返回端口或句柄。

```c
/**
 * @brief  为指定传输类型选择端口实现
 * @param  type    传输类型
 * @retval 成功返回只读端口，不支持的类型返回 NULL
 */
const transport_port_t *transport_factory_create(transport_type_t type)
{
    switch (type) {
        case TRANSPORT_TYPE_UART:
            return uart_transport_port();
        case TRANSPORT_TYPE_USB:
            return usb_transport_port();
        default:
            return NULL;
    }
}
```

工厂不动态分配对象，不隐藏复杂初始化失败；创建后的所有权和生命周期仍由组合根管理。

### 11.10 常见架构反模式

#### 万能 `main.h`

所有模块 include 一个聚合头，造成隐式依赖、循环包含和平台泄漏。替代方式是每个模块 include 自己直接使用的最小接口。

#### 全局可写状态

应用、ISR 和驱动直接读写同一个结构体，无法判断所有权和同步。替代方式是模块 API、快照、事件和单写者规则。

#### 上帝模块

`system.c`、`manager.c` 或 `control.c` 同时包含初始化、状态机、协议、算法和错误处理。组合根只负责装配；业务编排、服务和驱动分别归层。

#### 回调地狱

驱动回调直接调用业务，业务再调用另一个驱动，最终形成不可控 ISR 调用链。回调应转换成事件，复杂流程由显式状态机推进。

#### 无界队列和无界重试

为了“绝不丢数据”不断扩大缓冲或无限重试，最终耗尽内存或阻塞系统。所有队列、重试和等待都必须有上限与降级策略。

#### 每个模块一个任务

任务数量随文件数量增长，浪费栈并制造同步问题。任务代表独立调度和资源所有权，不代表源代码模块。

#### 伪抽象层

只把 HAL 函数一对一改名，却仍暴露相同句柄和语义，增加跳转而没有隔离变化。有效适配器应提供项目需要的能力和稳定契约。

#### 服务定位器滥用

任意模块通过 `system_get_xxx()` 获取任何设备，依赖图再次变成隐式全局网络。组合根注入依赖；仅在小项目或框架入口使用受控 getter。

### 11.11 模式引入检查

引入新的设计模式前记录：

- 当前具体问题和变化来源。
- 不使用模式时的真实成本。
- 新增 RAM、Flash、栈、队列和运行时开销。
- 调试路径是否更清晰。
- 最小项目能否裁剪。
- 主机测试或平台替换是否因此变得可行。
- 将来移除该模式需要修改哪些接口。

## 12. 裸机运行模型

### 12.1 主循环

**ARCH-SCHED-001 [MUST] — 裸机主循环只推进 Application/调度入口和必要的低功耗等待，不直接散列业务任务或用阻塞延时维持周期。**

周期与事件任务由 Services 中的调度机制决定，Application 负责注册本项目的任务及其运行约束。平台和应用初始化必须返回可处理状态；失败后进入已定义的安全、诊断或受限运行路径。

```c
/**
 * @brief  完成平台初始化并运行应用调度入口
 * @retval 正常固件运行期间不返回
 */
int main(void)
{
    app_status_t app_status;
    platform_status_t platform_status;

    platform_status = platform_init();
    if (platform_status != PLATFORM_STATUS_OK) {
        platform_enter_safe_halt(platform_status);
    }

    app_status = app_init();
    if (app_status != APP_STATUS_OK) {
        app_enter_safe_mode(app_status);
    }

    while (1) {
        app_run_once();
    }
}
```

`platform_init()` 只建立最小启动环境；各 Driver/BSP 在自身句柄和回调有效后按资源启用 IRQ/DMA。`platform_enter_safe_halt()` 是不返回的底层安全停机入口；`app_enter_safe_mode()` 完成模式转移后可以返回主循环继续提供受限诊断。两者必须保证危险输出处于安全状态，并根据项目策略受控复位、保持停机或提供有限诊断。

### 12.2 ISR 与 DMA

**ARCH-CONC-005 [MUST] — ISR/DMA 与主循环共享的数据必须有明确的原子性、内存可见性、cache 一致性和单写者/同步协议。**

ISR 允许读写硬件状态、清除中断、搬运数据、更新计数器和置事件；禁止复杂业务、循环等待、动态内存、日志格式化和不可证明的浮点路径。DMA 完成、错误和空闲事件通过回调或事件送到任务层处理。

中断优先级依据控制时序、数据完整性和可抢占性决定，不按外设名称机械排序。必须避免长时间关闭中断，并测量关键 ISR 的最坏执行时间。

### 12.3 临界区与原子性

优先采用单写者/单读者和不可变快照减少共享；需要保护复合操作时使用平台临界区。临界区必须尽可能短，不在其中调用阻塞函数、日志、驱动长事务或不可控回调。`volatile` 只解决编译器可见性，不保证复合读改写原子性。

### 12.4 注册式协作调度

**ARCH-SCHED-002 [MUST] — 协作调度器必须定义 release/deadline、优先级、漏周期、单次工作配额、过载和回调失败语义，并正确处理 tick 回绕。**

裸机默认使用注册式协作调度：Services 中的任务调度器维护统一单调时间、到期判断、分派优先级、事件状态和运行统计；Application 在初始化阶段注册具体任务、周期或触发源、优先级、允许的最大执行时间、deadline、单次工作配额及漏周期策略。调度器只调用已注册回调，不认识控制、通信或感知等产品任务；回调由 Application 任务入口实现，并调用 Domain 的功能 API。

协作式优先级只决定同一轮的分派顺序，不产生抢占；任何回调运行期间都会阻塞其他任务。周期任务默认使用 `next_release += period` 保持相位，不用 `now + period` 累积漂移。每个任务必须选择以下漏周期策略之一：跳过并处理最新输入、保留有限次数待处理 release、或在有界次数内补跑；控制任务不得无界补跑。跳过多个周期时一次计算并推进到未来的下一个 release，不能用无界循环逐周期追赶。

同优先级任务使用固定轮转或明确稳定顺序。事件消费者每次最多处理注册的工作配额，仍有积压时重新标记就绪，防止饿死其他任务。任务回调返回状态或更新任务健康记录；失败、WCET 超限、deadline miss 和连续积压达到项目阈值时，调度器记录统计并通知 Application 执行降级或安全策略，不能在调度器内部猜测产品行为。

任务集合通常在编译期确定，默认使用静态任务表和静态资源。时间端口由系统 Composition Root 注入调度器，调度器本体不直接调用厂商 `HAL_GetTick()` 或依赖具体定时器。时间比较遵守第 10.1 节，任务执行时间和 deadline miss 必须可测量、记录和上报。

### 12.5 Task 分类

| 类型 | 示例 | 调度方式 |
| --- | --- | --- |
| 事件消费者 | UART 解析、DMA 完成、传感器 FIFO | 有数据立即处理，单次限制工作量 |
| 固定周期控制 | PID、姿态更新、按键消抖 | 单调时钟或硬件周期事件 |
| 速率受限输出 | OLED、遥测、日志刷新 | 按最大输出频率运行 |
| 后台维护 | 参数保存、诊断、统计 | 低优先级、分片执行 |

输入消费者不应额外等待低频 tick，避免 FIFO 堵塞；固定周期算法也不能依赖主循环“碰巧足够快”。每次 task 处理的最大事件数应有限，防止高流量消费者饿死其他任务。

### 12.6 Tick 标志、计数和丢周期

简单项目可以由 ISR 置位标志、主循环读取并清除。可合并的状态更新可以使用单 bit 标志；不可丢失的事件必须使用计数器或队列。控制算法是否补跑由其时序语义决定：不允许补跑时只处理最新采样并记录错过周期；需要逐一处理的事件保留其数量与顺序。具体容器、容量与溢出策略属于项目级调度设计。

### 12.7 非阻塞的精确定义

非阻塞不等于“通常很快”。非阻塞 API 在一次调用中完成有限工作，不等待外部状态，并在可说明的上限内返回。异步操作通过状态、事件或回调通知完成。初始化阶段允许经过说明的短阻塞延时；运行阶段阻塞必须进入实时预算。

### 12.8 看门狗与任务健康

**ARCH-SCHED-003 [MUST] — 硬件看门狗必须由统一监督点根据运行模式、关键任务期限和系统进展决定是否喂狗，任务不得自行直接喂硬件看门狗。**

- 每个关键任务定义独立健康期限、启动宽限、允许漏报次数和适用运行模式。
- 事件任务只在有待处理工作时检查响应期限；不同周期任务不要求在同一个监督周期内同时打点。
- 只有当前模式所需的关键任务均未超期、调度器仍在推进且不存在要求复位的故障时才喂狗。
- 保存并上报复位原因，区分上电、看门狗、软件和掉电复位。
- 软件心跳允许合理抖动，不能因一次延迟立即复位。
- 调试版本不能长期关闭看门狗而让发布路径从未验证。

## 13. RTOS 运行模型

**ARCH-RTOS-001 [MUST] — RTOS 任务必须按实时约束、阻塞行为、故障隔离和资源所有权划分，不按源码文件或模块数量一一创建。**

RTOS 提供调度和同步能力。Domain 和声明为平台无关的 Services 不包含 RTOS 类型。任务边界按责任、时序和资源所有权划分；源码组件与 RTOS 任务不存在一一对应关系。

每个任务应能说明：

- 责任和输入事件。
- 优先级依据。
- 栈大小来源。
- 最大阻塞时间和最坏执行时间。
- 队列/通知容量。
- 共享资源和锁顺序。
- 超时和故障恢复。

必须识别优先级反转、死锁、队列满、任务饥饿和栈溢出风险。互斥锁只保护明确的共享资源，不用全局大锁包住整段业务。

### 13.1 任务划分

独立实时周期、可能阻塞的 I/O、故障隔离或明确生产者/消费者边界支持拆成独立任务。“这是一个模块”本身不足以创建任务。多个短小、同优先级、同周期模块可以由一个任务依次调度。

### 13.2 同步原语选择

**ARCH-RTOS-002 [MUST] — RTOS 同步必须为数据传递、资源互斥和事件通知分别选择语义匹配且有界的原语，并定义 ISR-safe 路径。**

| 需求 | 推荐原语 | 不推荐替代 |
| --- | --- | --- |
| ISR 唤醒一个任务 | 任务通知/二值信号 | 轮询共享布尔值 |
| 传递有序数据 | 有界队列/流缓冲 | 多个无所有权全局变量 |
| 保护共享资源 | 带优先级继承的互斥锁 | 长时间关中断 |
| 计数资源或事件 | 计数信号量 | 会丢事件的单 bit |
| 多条件状态 | 事件组或一致快照 | 多个无原子一致性的标志 |

ISR 只能调用 RTOS 提供的 ISR-safe API，并按要求请求上下文切换。普通互斥锁不能在 ISR 使用。

### 13.3 锁与死锁

共享资源规定唯一锁；多个锁存在嵌套时定义全局获取顺序。持锁期间不得等待队列、执行长 I/O、调用未知回调或睡眠。能通过消息所有权、单任务拥有设备或不可变快照解决的问题，不增加锁。

### 13.4 优先级和实时性

优先级按 deadline、周期、阻塞链和故障后果设置，不按“模块重要程度”主观排序。高优先级任务不得依赖低优先级任务的普通队列处理才能释放关键资源。必须观察响应时间、抖动、上下文切换和 CPU 空闲率。

### 13.5 栈、堆和任务退出

任务栈初值来自调用深度、局部数组、库函数和 FPU 上下文估计，再用高水位或填充检查验证。禁止只因栈溢出就盲目加倍。RTOS 对象优先静态创建；动态创建限定在启动阶段并检查失败。

永久任务通常不自行退出；确需退出时先停止事件来源、归还所有权、注销订阅并释放由它创建的资源。禁止删除仍被其他对象引用的任务或队列。

### 13.6 裸机/RTOS 统一端口

```c
typedef struct {
    event_queue_status_t (*post)(
        void *queue,
        const event_t *event,
        uint32_t timeout_ms);
    event_queue_status_t (*post_isr)(
        void *queue,
        const event_t *event,
        bool *should_yield);
    event_queue_status_t (*receive)(
        void *queue,
        event_t *event,
        uint32_t timeout_ms);
} event_queue_port_t;
```

队列状态至少区分成功、满/空、超时、非法上下文和内部错误；`post_isr` 不接受阻塞超时。Domain 通常不直接持有 RTOS 队列类型；Application、Services 或调度适配代码负责事件传递。操作系统抽象只覆盖项目实际使用且需要替换的能力。

## 14. 通信架构

**ARCH-COMM-001 [MUST] — 通信链必须分离硬件传输、器件协议、项目帧/会话和业务语义，并为每段规定所有权、容量、超时和错误边界。**

通信模块分为传输、帧处理和领域处理：

```text
硬件/DMA → 传输缓冲 → 帧边界检测 → 协议解析 → 命令/数据模型 → Domain
```

- 传输层只负责字节可靠搬运和错误。
- 帧层负责长度、校验、转义、版本和超时。
- 协议层负责命令语义和响应。
- Domain 决定命令是否允许以及执行什么产品行为。
- 接收、解析和执行可异步，禁止在 ISR 中完整解析复杂协议。
- 缓冲区大小、溢出策略、最大帧长和超时必须明确。

默认分区映射如下：

| 内容 | 默认归属 | 边界 |
| --- | --- | --- |
| UART/SPI/I2C、DMA 和字节搬运 | Driver/BSP | 不理解项目命令 |
| 外部器件固定寄存器/线协议 | Device Driver | 只表达器件原生能力 |
| CRC、COBS、Base64、FIFO 等通用实现 | Libraries | 无产品状态和 I/O 所有权 |
| 项目帧、会话、重传和连接状态 | Protocol Service | 不决定业务命令是否允许 |
| 命令权限、模式和产品响应 | Domain/Application | 不接触 HAL/DMA 句柄 |
| 第三方完整通信栈 | Middleware | 项目适配与上游源码分离 |

### 14.1 UART RX：DMA、空闲检测与环形缓冲

推荐数据流：

```text
UART → DMA 临时缓冲 → IDLE/RX Timeout/定期余量检测
     → RX 环形缓冲 → 帧解析器 → 协议消息
```

STM32 可以使用 IDLE 或接收超时事件；没有硬件空闲检测的平台可以周期读取 DMA 写入位置，把当前新增字节作为一个处理批次。批次边界不等于协议帧边界，解析器必须接受任意分块。平台差异集中在 UART 适配器，环形缓冲和解析器保持通用。

环形缓冲只提供调用方实际使用的最小 API；典型接口包括 `init`、`push`、`pop`、`available` 和溢出计数，`free`、`clear`、批量读写或零拷贝视图按需求增加。保留一个空位是简单可靠的满/空判定方案：

```c
typedef struct {
    uint8_t *data;
    uint16_t capacity;
    volatile uint16_t read_index;
    volatile uint16_t write_index;
    volatile uint32_t overflow_count;
} ring_buffer_t;

/**
 * @brief  在 ISR 上下文向环形缓冲区写入一个字节
 * @param  buffer    已初始化的环形缓冲区
 * @param  value     待写入字节
 * @retval 写入成功返回 true，缓冲区已满返回 false
 */
bool ring_buffer_push_isr(ring_buffer_t *buffer, uint8_t value)
{
    uint16_t next = (uint16_t)((buffer->write_index + 1U) % buffer->capacity);

    if (next == buffer->read_index) {
        buffer->overflow_count++;
        return false;
    }

    buffer->data[buffer->write_index] = value;
    buffer->write_index = next;
    return true;
}
```

生产者只写 `write_index`，消费者只写 `read_index`。如果目标架构不能保证索引宽度的原子访问，或存在缓存/多核，必须增加平台同步。ISR 搬运量过大时采用 DMA 双缓冲或零拷贝描述符，不能在高优先级 ISR 中逐字节复制无限数据。

### 14.2 UART TX：队列与 DMA 链式发送

上层通信组件通过 BSP 通信能力或传输端口提交完整消息/字节；BSP/Driver 写入有界 TX 队列，发送空闲时启动一批 DMA；DMA 完成 ISR 只更新读位置并触发下一批。必须明确：

- 写入接口是全有或全无，还是允许部分写入。
- 多调用者的消息是否需要原子入队。
- 队列满时返回 `BUSY`、等待有限时间还是丢弃低优先级消息。
- DMA 正在读取的内存不得被调用者修改。
- 发送错误后如何丢弃、重试或重新同步。

### 14.3 帧解析状态机

解析器逐字节或逐块消费，不依赖一次 DMA 回调恰好得到完整帧。典型状态包括等待帧头、读取头部、读取载荷、读取校验和、完成和丢弃。

```text
WAIT_SYNC → READ_HEADER → READ_PAYLOAD → READ_CHECKSUM → COMPLETE
     ↑              任意长度/校验/超时错误 → DISCARD ─────┘
```

解析规则：最大帧长在分配或复制前检查；超时后复位到同步状态；校验失败累计诊断计数；未知命令由协议层返回明确错误，不由传输层决定业务响应。

### 14.4 SPI 与 I2C 事务

**ARCH-COMM-002 [MUST] — 共享总线必须有唯一仲裁所有者；事务必须携带设备、缓冲区、长度、deadline、完成通知和取消/错误语义。**

底层总线由一个 MCU 外设 Driver 或 BSP 仲裁点拥有，多个设备通过事务对象提交访问。事务包含设备、操作、地址、缓冲区、长度、超时和完成通知。跨层总线服务只依赖 BSP 能力或总线端口，不持有厂商句柄。不得由不同模块直接持有同一个 HAL 总线句柄并各自启动 DMA。

I2C/SPI 错误恢复按平台能力执行：停止事务、清错误、复位外设、必要时恢复总线，再让上层决定重试。重试必须有限且不能在 ISR 内循环完成。

### 14.5 协议版本和兼容性

**ARCH-COMM-003 [MUST] — 跨设备协议和持久化格式必须定义兼容面、版本策略、长度上限、字节序、完整性校验和未知字段/命令行为。**

持久化或跨设备协议 SHOULD 含版本字段。新增可选字段保持旧解析器可跳过；改变字段语义或字节布局时升协议主版本。协议结构不能直接序列化编译器结构体，必须显式处理字节序、长度和校验。

## 15. 错误处理与恢复

**ARCH-ERR-002 [MUST] — 模块必须区分正常操作状态、可恢复技术错误和系统故障，并通过返回值或有界事件传播，不能静默吞掉失败。**

`BUSY`、`NO_DATA`、队列空和有限重试中的暂态结果通常属于操作状态，不自动进入系统错误队列。技术错误至少按适用能力区分参数、状态、超时、传输、硬件和资源错误；同一错误持续存在时使用状态变化、计数或限流事件报告。

错误处理分为三层：

1. **检测/传输**：模块产生技术状态、来源、错误码和必要上下文，不决定产品级严重度。
2. **映射/诊断**：BSP、Domain 或 Application 根据能力影响映射系统严重度；诊断服务负责记录、显示或发送，不直接修改 Driver 内部状态。
3. **处理/恢复**：Application 或系统策略决定重试、复位、降级、停机或继续运行。

恢复动作必须幂等；重试次数、退避、超时和最终失败状态必须有上限。错误处理本身不得造成循环重试、队列无限增长或看门狗失效。

### 15.1 错误对象

```c
typedef enum {
    /* 诊断信息，不影响当前能力。 */
    SYSTEM_FAULT_SEVERITY_INFO,
    /* 异常预警，系统仍可运行。 */
    SYSTEM_FAULT_SEVERITY_WARNING,
    /* 需要执行受控恢复的故障。 */
    SYSTEM_FAULT_SEVERITY_RECOVERABLE,
    /* 必须停机或复位的致命故障。 */
    SYSTEM_FAULT_SEVERITY_FATAL,
} system_fault_severity_t;

typedef struct {
    uint16_t source;
    uint16_t code;
    uint32_t context;
} component_fault_t;

typedef struct {
    component_fault_t fault;
    system_fault_severity_t severity;
    uint32_t timestamp_ms;
} system_fault_event_t;
```

错误来源 ID 由项目集中注册，错误码由模块定义。组件产生 `component_fault_t`；BSP、Domain 或 Application 的错误映射表根据当前模式和能力影响补充时间与严重度，生成 `system_fault_event_t`。不要用一个 32 位位图假设错误源永远少于 32 个；最小项目可以使用位图，规模扩大时切换到固定事件队列和每源状态表。

### 15.2 错误传输

同步错误首先通过函数返回值交给直接调用者；异步硬件错误通过错误事件传输。驱动可以记录寄存器快照等诊断上下文，但不直接操作 OLED、蓝牙或业务状态。

错误队列必须防止相同持续故障无限重复入队。常用策略是每个来源维护当前状态和 `queued` 标志；状态变化或经过限流周期后才再次上报。

### 15.3 上报与诊断

上报层把错误转换为日志、屏显、遥测或复位记录。格式化和 I/O 在任务上下文完成。资源不足时优先保留致命错误和首次错误，后续重复只增加计数。

### 15.4 恢复策略

| 故障 | 常见策略 |
| --- | --- |
| 短暂总线错误 | 清错误、有限重试、退避 |
| 传感器持续失联 | 重新初始化、使用降级数据、禁止相关功能 |
| 电机/执行器异常 | 立即安全输出，等待应用确认恢复 |
| 参数或状态错误 | 拒绝操作、记录上下文，不盲目复位硬件 |
| 内存/栈/内部不变量 | 保存最小诊断并安全复位或停机 |

ISR 可完成硬件必须立即执行的安全动作和最小复位；完整恢复由任务状态机处理。错误清除只在故障条件真正消失、恢复验证通过后执行。

### 15.5 故障状态机

关键设备推荐使用 `NORMAL → DEGRADED → RECOVERING → NORMAL/FAILED` 状态机。恢复次数和时间窗口有上限；超过上限进入 `FAILED`，等待人工操作、系统重启或更高层策略，禁止无限重初始化。

## 16. 内存、资源与实时性

**ARCH-RES-002 [MUST] — 项目必须为关键路径维护可测量的 CPU、deadline、内存、栈、缓冲区、带宽和适用功耗预算。**

默认优先使用静态分配、调用者提供的缓冲区和固定大小对象池。动态内存只有在平台、生命周期、最大占用、碎片风险、失败处理和释放责任都明确时才可作为例外。

每个标准项目至少记录关键资源：

| 资源 | 必须说明的内容 |
| --- | --- |
| Flash | 固件、常量、引导和升级空间 |
| RAM | 全局、堆、栈、DMA 和缓存 |
| 栈 | 每个任务或关键调用链的上限 |
| CPU | 周期、最坏执行时间和中断占用 |
| 通信 | 速率、最大帧、FIFO 深度和丢包策略 |
| 功耗 | 睡眠、唤醒和高负载状态（适用时） |

控制输出采用分层防护：Driver 保证寄存器和器件命令处于硬件合法范围；BSP 保证板卡的电气、机械方向和执行器安全范围；Domain 保证产品运行范围和业务约束。每层只能依赖自己拥有的知识，不能用上层校验替代下层保护。输出可能饱和时，PID 等算法需要积分抗饱和和异常输入保护。看门狗在统一的位置喂狗，并在复位后记录复位原因。

### 16.1 静态内存布局

长期对象在组合根或模块中静态分配；大型 DMA 缓冲区根据平台要求放入正确的内存区和对齐边界。链接脚本中的 RAM 区域、栈、堆、DMA 不可访问区和保留区必须与芯片实际一致。

### 16.2 对象池

需要运行期创建有限数量消息、事务或帧时，使用固定对象池：

- 容量由峰值并发需求和安全余量决定。
- 获取失败返回明确错误，不能返回未初始化对象。
- 对象归还前清除所有权和链表状态。
- 调试版本检测重复释放、越界和池泄漏。
- ISR 使用的池操作必须有确定时间且并发安全。

### 16.3 动态内存例外

ESP32 网络栈、文件系统或第三方组件可能依赖堆。项目允许保留第三方内部动态分配，但应用代码应限制：

1. 尽量只在启动阶段分配。
2. 记录最大堆占用和最低剩余堆。
3. 检查每次可失败分配。
4. 禁止 ISR 和硬实时控制路径分配。
5. 长时间压力测试碎片和失败恢复。

### 16.4 实时预算表

**ARCH-RES-003 [MUST] — 周期或事件关键执行单元必须记录触发条件、deadline、WCET、抖动/响应时间和超限动作，并用目标构建测量更新。**

| 执行单元 | 周期/触发 | Deadline | WCET | 抖动 | 超时动作 |
| --- | --- | --- | --- | --- | --- |
| 控制环 | 5 ms | 5 ms | 待测 | 待测 | 安全输出/记录丢周期 |
| UART RX | DMA/IDLE | FIFO 溢出前 | 待测 | 不适用 | 复位解析器 |
| OLED | 50 ms | 200 ms | 待测 | 可容忍 | 跳过本帧 |

数字由项目测量填写，规范不硬编码“所有控制环必须多少 Hz”。周期来自系统带宽、数据到达率和用户感知要求，并保留 CPU 余量。

### 16.5 安全输出与限幅

**ARCH-RES-004 [MUST] — 危险执行器必须在复位、初始化、未授权、停止、错误和看门狗路径中具有可验证的安全状态及不依赖普通队列的停机路径。**

- Driver 在写寄存器或发送器件命令前限制硬件合法范围。
- BSP 在输出前限制板级电气、机械和安装相关的安全范围，并处理有效电平和方向。
- Domain 在生成命令时限制产品运行范围；Application 决定模式授权和系统级停机。
- 可能饱和的闭环算法包含抗饱和、输出限幅和异常采样处理。
- 传感器超范围、NaN、校验失败或过期样本不得直接进入控制输出。
- 紧急停机路径不依赖普通任务队列有空位。

## 17. 平台集成与条件系统能力

### 17.1 生成代码

**ARCH-DEP-009 [MUST] — 生成代码、第三方源码和手写平台适配必须具有可追溯且可重新生成/重建的边界。**

STM32CubeMX、TI SysConfig 和其他配置工具生成的文件默认隔离且禁止手改。工具配置、版本和生成命令必须可追溯；手写实现放在用户目录、BSP 或适配层。若工具无法避免修改生成文件，必须记录生成后需要重新应用的补丁或人工步骤。

### 17.2 平台差异

平台差异集中在厂商 SDK/HAL、BSP、Drivers 和端口适配器。Domain、算法库和声明为平台无关的 Services 不使用平台宏控制核心逻辑。`#ifdef` 优先出现在平台边界，嵌套不超过两层；同一能力在不同平台的语义必须保持一致，无法一致时在 API 文档中明确差异。

### 17.3 从裸机迁移到 RTOS

优先迁移顺序：时间/事件端口 → 通信和缓冲 → 设备任务 → 服务任务 → 应用编排。领域算法和状态机应尽可能保持不变；需要重写的部分通常是调度、同步、生命周期和错误恢复。迁移后重新评估栈、优先级、队列深度和最坏延迟。

### 17.4 外部通信与安全边界

**ARCH-SEC-001 [MUST] — 存在不可信输入或外部控制通道时，项目必须定义信任边界、身份/权限要求、资源上限和验证失败行为。**

所有外部长度、索引、命令、持久化记录和升级元数据在进入内部模型前完成边界、版本、完整性和权限校验。解析成功不代表命令被授权；Domain/Application 根据当前模式、设备状态和权限决定是否执行。认证失败、重放、速率超限和资源耗尽必须有有界处理，不能因攻击流量阻塞控制路径或无限写日志。

密钥、令牌和设备身份不写入源码、普通日志或可读参数服务。其存储、注入、轮换和擦除方式由平台安全能力与项目威胁模型决定。没有外部不可信边界的项目可以将本节标记为不适用，但仍须验证本地调试接口和生产配置不会意外开放控制能力。

### 17.5 Boot 与固件升级

**ARCH-UPD-001 [MUST] — 支持 Bootloader 或固件升级的项目必须定义镜像兼容性、完整性/真实性、掉电一致性、启动确认、失败回滚和执行器安全状态。**

镜像元数据至少标识产品、目标板/硬件修订版、版本、长度和完整性信息；存在不可信分发路径时必须验证数字签名或等价真实性。升级不能覆盖唯一可启动镜像后再依赖同一次写入成功；使用 A/B、恢复镜像或经过验证的原子切换方案。新镜像只有在完成启动自检和关键能力确认后才标记有效，连续启动失败必须进入回滚、恢复或诊断路径。

Bootloader、应用、通信协议和持久化 Schema 的兼容范围必须共同记录。防回滚只在威胁模型要求时启用，并必须保留受控恢复路径；安全输出在升级、校验、回滚和恢复模式中始终有效。

### 17.6 低功耗、时钟和电源域

**ARCH-PWR-001 [MUST] — 使用睡眠、动态时钟或外设电源域的项目必须用显式状态机管理进入条件、唤醒源、时间连续性、未完成事务和恢复顺序。**

进入低功耗前，各资源所有者必须停止或挂起新事务，处理 DMA/总线的完成或取消，保存需要保留的状态，并确认唤醒源已配置。唤醒后按依赖图恢复时钟、内存、外设、Driver/BSP 能力和任务 deadline；不能假设外设寄存器、DMA 位置或软件 tick 自动保持有效。

动态时钟切换必须重新验证波特率、定时器、控制周期和超时换算。功耗状态转换的最坏延迟、能耗收益和失败恢复需要测量；不使用低功耗或动态时钟的项目记录为不适用即可。

### 17.7 多核、cache 与 DMA 一致性

**ARCH-CONC-006 [MUST] — 存在多核、数据 cache 或非一致 DMA 时，所有共享内存必须定义所有者、内存区域、同步原语、cache 维护方向和屏障位置。**

DMA 缓冲区必须满足平台的可访问区域、对齐和 cache-line 要求。CPU 向 DMA 交付数据前执行适用的 clean，DMA 向 CPU 交付数据后在 CPU 读取前执行适用的 invalidate；具体顺序以芯片和工具链文档为准。描述符、数据缓冲和完成标志分别评估，不能只给指针添加 `volatile`。

多核共享对象优先采用消息所有权和单写者模型；确需共享可写状态时使用目标平台原子操作、锁和内存顺序。主机测试不能替代目标 cache/DMA 验证；没有相关硬件特性的项目记录为不适用。

## 18. 测试与架构审查

### 18.1 测试层次

**ARCH-TEST-001 [MUST] — 测试必须沿适用的模块、平台适配、BSP 集成、系统和发布边界覆盖成功路径、边界条件和故障路径。**

- 纯算法、独立 Domain 和平台无关产品逻辑：主机单元测试和边界测试。
- 服务和协议：模拟时间、传输和错误，验证状态机与超时。
- 驱动：端口替身、仿真器或目标板测试。
- 系统：真实硬件冒烟、故障注入、长时间运行和资源观察。
- 发布：确认构建选项、版本、烧录文件、日志和回滚信息。

### 18.2 必测场景

#### 状态机

- 正常完整转移。
- 每个等待状态超时。
- 非法事件和非法状态。
- 取消、重试和恢复次数耗尽。
- tick 回绕附近的 deadline 判断。

#### 缓冲与通信

- 空、满、回绕、单字节和最大批量。
- DMA 数据跨多次回调组成一帧。
- 一次回调包含多帧。
- 错误长度、校验失败、半帧超时和噪声后重新同步。
- RX/TX 队列满及其诊断计数。

#### 并发

- ISR 在消费者读取边界时写入。
- 队列满、任务超时和锁竞争。
- 高优先级任务被低优先级资源阻塞。
- 任务栈高水位、看门狗和错误恢复同时发生。

#### 硬件

- 设备未连接、总线卡死、电源重启和通信中断。
- 传感器极值、执行器限幅和安全停机。
- 冷启动、重复初始化、软件复位和看门狗复位。

### 18.3 主机测试边界

**ARCH-TEST-002 [SHOULD] — 平台无关 Domain、Libraries、解析器、状态机和 Services 应能在主机目标中编译并使用可控替身测试。**

Domain、算法库、协议解析、环形缓冲和声明为平台无关的 Services SHOULD 在主机编译。时间、传输、存储和硬件端口用替身注入。测试替身必须可控制成功、忙、超时、错误和调用顺序，覆盖正常与失败路径。

### 18.4 硬件在环

HIL 至少记录固件版本、板卡版本、连接方式、输入刺激、预期输出、超时和日志。自动化价值最高的场景是烧录后冒烟、通信回环、传感器断连、看门狗和关键执行器安全状态。

### 18.6 架构产物与持续符合性

**ARCH-GOV-006 [MUST] — 标准及完整项目必须维护能够解释当前实现的项目架构说明，并把关键需求、架构决策、公共能力和验证证据连接起来。**

- 系统目标、边界、外部参与者、硬件目标和重要约束。
- 实际分区/目录映射、依赖图、系统 Composition Root 和公共能力。
- 启动/关闭、安全输出、主要运行模式、任务、ISR、事件和数据流。
- 关键质量属性场景、实时与资源预算、错误传播和降级路径。
- 参数、持久化、协议兼容性，以及第 3.4 节条件主题的适用性结论。
- 架构决策记录、规则例外、测试证据和已知风险。

**ARCH-TEST-003 [MUST] — 架构边界必须通过构建目标、依赖检查、静态分析、测试或审查清单中的可重复证据持续验证。**

架构说明不复制本规范全文，只记录本项目的选择、映射和证据。接口、任务、硬件或质量属性发生架构意义的变化时，同一修改必须更新相应说明或 ADR；项目定期检查实现依赖是否偏离文档。
